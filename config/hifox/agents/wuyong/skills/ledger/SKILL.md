# Dispatch Ledger（调度台账）

吴用的跨会话工作记忆。会话历史会随 `/new`、运行时重启或上下文压缩消失；台账是唯一的跨会话权威记录。

**形态：文件夹式一事项一文档**——状态 = 所在文件夹，索引 = 文件夹列表，详情 = 事项正文；**不存在共享的可变「总台账」文档**。这样并发写互不相撞、每轮读取量只与未完结事项数相关，不随历史增长。

## 0. 设计约束（平台事实，不要改写成别的形态）

- `docs document edit` 整文替换、**无版本锁**（服务端按次留版本快照，但 CLI 读不到），没有 CAS / If-Match / 文档锁。
- `docs search` 只搜**文档名**，不搜正文。
- 同一会话的 run 由服务端按**队首 claim** 串行化（后续 run 排队，不是靠唯一索引），**并发只发生在不同会话之间** → 按「事项」划分单一写者即可无锁。
- 因此禁止：共享索引文档、共享「当前状态」文档、全量读取历史后再重写台账。

## 1. 生命周期与文件夹（完备划分）

每个事项在任一时刻**恰好属于一个**文件夹：

| 生命周期状态 | 文件夹 | 判定 |
|---|---|---|
| 计划中，未启动 | `计划` | 有明确的触发条件 / 时间；无平台对象在跑 |
| 等待用户决定 | `等待用户` | 是否建任务（含已提议待确认的交付）、是否重试、是否继续，等用户答复 |
| 活跃或等待非用户主体 | `进行中` | 未收口：平台对象存在且非终态（workflow 非终态 / 任务未关闭），**或终态已发现但尚未向用户转述**（`状态：待转述（verdict）`）；等待专家也算进行中 |
| 终态（成功 / 失败 / 取消 / 重复） | `已收口/<YYYY-MM>` | 已转述且不再有后续动作；时间线末行写 `结论：<verdict> · …`，文件名带 `· <verdict>` |

- **收口 = 转述之后**：后台巡检查到终态时**不归档**，只把事项标成 `状态：待转述（verdict）` 留在 `进行中`；下一次用户对话先转述，再按 verdict 归档（失败 / 取消在转述后先移入 `等待用户`，用户放弃才归档）。

- **终态不叫「已完成」**：`已收口` 同时容纳成功、失败、取消、重复，避免语义误导；verdict 写在文件名与时间线末行，列表即可分辨。
- **失败但可能重试**不是终态：先放 `等待用户`（问是否重试），或留在 `进行中`（已决定重试并追加新 execution）；只有「不再有任何后续动作」才收口。
- **`待转述` 不是「无执行者」**：它是已终态、待交付；异常检测只针对非终态或失联对象，别把两者混为一谈。
- **重复收口**：同一事项被重复派发 / 建项时，保留最早一条为主项，其余以 `重复` 收口，结论行写 `关联项=<主项 id>`；不删除任何文档。
- **同轮办完的杂活不建文档**：一两条只读查询、转述、查状态直接答完即止；咨询类派发仍建事项（有执行对象），归档后可追溯。
- **待确认的交付提议要建文档**：咨询结论里给出的建任务提议（含 `主题` / `实例` + 范围 / 验收）物化为 `等待用户` 事项——`/new` 之后后继会话没有任何对话历史，提议不落账则用户回「建吧」时无从判定指代谁。
- **改进项决策事项**：用户采纳 / 放弃夜间自省的改进项时，新建 `进行中`（有实现任务 / 执行）或 `计划`（等维护者改配置）事项，正文写 `改进项：<I-...>`、`决策：采纳|放弃`、`owner`、`验证窗口`；需要实现时按 §4 建任务。该事项按普通台账生命周期收口（实施对象终态后转述并归档）；反思者从开放事项或当前 / 上月 `已收口` 读取决策，验证由改进项文档独立跟踪；不要直接改反思者的改进项文档。
- **不按会话拆文件**：一个会话可产生多个事项；同一事项可被后续会话读取 / 接管。

## 2. 状态真值与异常处置

你在用户对话中运行；两次对话之间**本会话不做任何轮询**（后台巡检是另一个 run，见 §11）。文件夹里的状态是「最后一次核对的结果」，不是实时状态：

- 回答任何「进展 / 在跟什么 / 怎么样了」之前，必须在本轮重新查询，**不许拿正文当现状**。
- 每条事项记录 `最近核对：<ISO>`；超过 24h 未核对 → 先核对再引用。
- **写入 `进行中` 的充分必要条件**：本轮查询成功，且平台对象存在——非终态，或终态已标 `状态：待转述（verdict）` 且尚未转述。否则只能写 `等待用户`（待决策）或 `已收口`（已转述的终态）；读到的 `进行中` 只是上次核对结果。
- **派发命令成功但拿不到 execution id**（超时 / 输出不可解析）→ 不许写「进行中」：标 `状态：派发结果未知`，用 `hifox workflow logs list --workflow <id> --space "<Space>" --filter '{"startDate":"<10 分钟前>"}' --output json` 找回 execution id；找不到就转 `等待用户`（重派 / 取消），绝不假设已在跑。

异常分类与处置（**发现即报，绝不自动重试**）：

| 异常 | 判定 | 处置 |
|---|---|---|
| 派发结果未知 | 无 execution id，且时间窗清单里找不到 | `等待用户`：重派或取消 |
| 幻影项 | 有 id，`runs view` 非零退出且 stderr 含 `Execution not found`（404），且 `logs list --space "<Space>" --filter '{"executionId":"<id>"}'` 为空 | 标 `状态：执行不存在` → `等待用户` |
| 瞬时失败 | `runs view` 终态 `failed`，`totalDurationMs` 极短或 error 指向启动失败 | 标 `待转述（失败）`；前台转述后移入 `等待用户`（问重派 / 转任务 / 取消）；不自动重试 |
| 卡住 | `pending`（排队）超过 10 分钟，或 `running` 超过 120 分钟 | 标 `状态：疑似卡住（时长）`；`workflow logs view <execution-id> --space "<Space>"` 取诊断后报给用户 |
| 暂停待输入 | `runs view` 的 `paused` 非空，或 `hifox workflow runs paused <workflow-id> --space "<Space>"` 列出 | `hifox workflow runs pause <workflow-id> <execution-id> --space "<Space>"` 读等待输入，转述给用户 |
| 已取消 | `runs view` 终态 `cancelled`；或任务状态为取消 / 拒绝 | 标 `待转述（取消）`；前台转述后移入 `等待用户`（问后续），用户放弃才归档；不再重试 |
| 任务终止 | 任务已关闭（完成 / 发布 / 取消 / 拒绝 / 关闭） | 完成 / 发布 → `成功`；取消 / 拒绝 → `取消`；其它关闭但语义不明 → `等待用户`，不猜 verdict |
| 任务无执行者 | 任务未关闭，但 `delegate` 为空且无人类 assignee；或 delegate 已归档（`hifox agent list --output json` 的 `archivedAt` 非空） | `等待用户`：重新委派或取消 |

- **自动修复仅限状态真值**：终态 → 标 `待转述`（由前台转述后收口）；幻影 / 未知 → `等待用户` 并写明原因。**重派、取消、转任务一律等用户决定。**
- **后台巡检的写权限**：只追加终态结论行，更新 `状态` / `最近核对` / 时间线；终态一律只标 `待转述（verdict）`，**不改名、不移动、不归档**——它无法把结果送到用户面前，收口必须由前台对话完成。已是 `待转述（同 verdict）` 的事项只刷新 `最近核对`，不重复追加结论。
- `runs view` 的其它非零退出（网络 / 5xx）按「查询失败」处理（先重试一次），**不得**判成幻影或不存在。
- 每轮回复开头先报异常（最多列 3 条，其余给数量），再答用户问题；异常项状态必须带「最近核对」时间。
- 用户隔很久后的第一条消息：先做全量对账（所有未完结事项），开头交代「自 <上次核对时间> 以来：N 项完成、M 项异常」。

## 3. 记忆分层（对齐市面做法）

| 层 | 载体 | 何时读 | 容量策略 |
|---|---|---|---|
| 热层（未完结工作） | `计划` / `等待用户` / `进行中` 的文件夹列表（每轮）+ 事项正文（进行中必读，其余按需） | 每轮 / 按需 | 只随未完结事项增长；>20 项提示积压 |
| 温层（已收口） | `已收口/<YYYY-MM>/` 月份文件夹 | 用户问历史时按需 | 永不自动加载；只列月份、定点读命中项 |
| 冷层（平台真值） | `workflow runs view` / `task view` / `workflow logs list` / `run list` | 对账时按关联键现查 | 不复制进台账，只存关联键 |

- 对照：OpenClaw 的 curated core（常驻、受预算截断）+ episodic 日记（不进 bootstrap、按需检索）+ dreaming 整合；Hermes 的硬性字符上限（写超即报错，迫使同轮整合）+ 冻结快照 + `session_search` 兜底。本台账取同一结构：**常驻层只放未完结工作，历史只按需检索。**
- 平台没有 embedding/FTS 检索，所以「可检索性」由**文档名**承担：事项名必须含主题 + 标题关键词，收口时补 verdict。

## 4. 目录与命名

```text
Agents/                                  # HiFox 产研 Space 的共享文档集
  <部署名>/                              # 每个部署副本（agent 实例）一个文件夹，如「吴用 (staging)」
    进行中/
    等待用户/
    计划/
    已收口/
      2026-11/                          # 按自然月
```

- 事项 id：`D-<YYYYMMDD-HHMMSS>`（时间戳到秒；建前查重时若目标文件夹已有同 id 前缀——同秒并发——追加 `-2/-3`）；计划项用 `N-<YYYYMMDD-HHMMSS>`。
- 未完结文档名：`<id> · <主题> · <标题关键词>`（如 `D-20261110-142005 · xwing · 登录页 500 排查`）。
- 收口文档名：追加 ` · <verdict>`，verdict 取 `成功 | 失败 | 取消 | 重复`。
- 状态只由文件夹表达；改名只用于收口 verdict，不用来表达进度。
- 文件夹按**精确名**解析，缺失才创建；列表里出现同名重复文件夹时用第一个，**不要删除**（删除会级联删子文档）。

## 5. 读取（每轮，容量有界）

```bash
# 1) 文档集（权限看 canWrite）
hifox docs shared list --space "HiFox 产研" --output json
# 2) 实例文件夹 → 解析状态文件夹（名字精确匹配）
hifox docs list --shared <文档集 id> --output json
hifox docs list --shared <文档集 id> --parent <实例文件夹 id> --output json
# 3) 读未完结事项（进行中必读；等待用户/计划按需）
hifox docs list --shared <文档集 id> --parent <进行中 id> --output json
hifox docs document view <事项文档 id> --shared <文档集 id> --output text
```

- 每轮只 view `进行中` 的事项（O(未完结)），不读 `已收口`；`等待用户` / `计划` 的正文只在需要跟进 / 回答时展开。
- 三个未完结文件夹的**列表**（每轮已读）同时是主题判定级 4（「唯一未完结」）的候选来源，但**不等于**会话焦点（级 3 只认本会话内的判定结果）；判定细则在 `{{skills.wuyong/topic-resolution.name}}` skill，本 skill 只负责这些事项的读写与状态真值。
- 用户问「上次 / 之前 / 历史」时：`hifox docs list --shared <id> --parent <已收口/<YYYY-MM> id>`，或 `hifox docs search "<关键词>" --shared <文档集 id> --output json`，只 view 命中项。
- 禁止把整月/全年归档读进上下文；按月收敛，需要更细再定点读。

### 首次使用：自举目录（缺失才创建）

实例文件夹或任一状态文件夹不存在时（按精确名 list 确认），只建空文件夹、不建事项：

```bash
# 实例文件夹：父级 = 文档集根
hifox docs folder create --name "<部署名>" --shared <文档集 id> --output json
# 四个状态文件夹：父级 = 实例文件夹
for name in 进行中 等待用户 计划 已收口; do
  hifox docs folder create --name "$name" --shared <文档集 id> --parent <实例文件夹 id> --output json
done
```

- 并发重复创建：先 list 后 create；出现同名重复时用第一个，**不删除**。
- 自举失败（权限 / CLI 错误）才按 §10 降级；「不存在」不是失败。

## 6. 事项正文模板

```markdown
# <事项 id> · <标题>

- 类型：workflow | task | chore
- 意图：咨询 | 交付
- 主题：xwing | x-deploy | apifox | docs-site | apifox-cli | 杂活
- 实例：hifox | sharkly | apifox | apidog | apidog-eu | apifox-cli | apidog-cli | PDV/<产品线> | 未指定（值域与别名见 `{{skills.wuyong/topic-resolution.name}}` skill §3）
- 判定依据：主题=<显式词|指代事项|会话焦点|唯一未完结|澄清> · 实例=<显式词|指代事项|会话焦点|澄清>
- 状态：<执行中 | 等待专家 | 阻塞（原因） | 派发结果未知 | 执行不存在 | 疑似卡住（时长） | 待转述（成功|失败|取消） | 等待用户（等什么）>
- 请求：<用户原话要点，一行>
- 关联键：space=<Space 名> · workflow=<id> · execution=<id>
  或：task=<任务号>
- 关联项：<父事项 / 同主题事项 id，可选>
- 改进项：<I-YYYYMMDD-NN> · 决策：<采纳 | 放弃>（仅夜间自省改进项决策事项；改进项文档由反思者单写）
- 创建：<ISO8601> · 归属会话：<chatSessionId；`hifox run view $HIFOX_RUN_ID --field chatSessionId`>
- 最近核对：<ISO8601>（本轮查询结果：<status>）

## 时间线
- <ISO8601> 派发（execution=<id>）
- <ISO8601> 查询：running
- <ISO8601> 重试（execution=<id2>）
- <ISO8601> 结论：<verdict> · <交付物 / 结论 / 链接>
```

- 正文只存「请求要点 + 关联键 + 时间线 + 结论」，不复制平台大段输出；专家答复原文在转述后可不入库。
- `归属会话` = 当前会话 id，**只作来源追溯**（这个事项由哪个会话开的）：`/new` 后旧会话对 agent **不可读**（agent run 只能读自己绑定的那个会话），所以它不是跨会话记忆，也不是回读入口。会话消息另受创建者 / 参与者 / `manage` 门槛保护，但 id 仍按内部句柄对待：只记 id、不记会话内容。
- `主题` / `实例` / `判定依据` 由主题判定填入（阶梯与词表见 `{{skills.wuyong/topic-resolution.name}}` skill，本 skill 只存结果）；**巡检不填、不改这三个字段**。
- **永不入账**：任何密钥 / 凭据 / 环境变量值 / 机器标识（Computer / Lease / Runtime ID、主机名、IP、路径）。需要引用时只写环境变量名或「凭据已配置」；上游报错先脱敏再写入。私有化实例默认只写客户代号或版本，**真实客户名仅在用户明确要求时写入**。
- 收口时最后一行必须写 `结论：<verdict> · …`，与文件名 verdict 一致。
- `最近核对` 每次对账都更新；没有本轮查询证据，不允许把状态写成「执行中」。

## 7. 写入

1. **建前先查重**：`docs list` 三个未完结文件夹，按主题 + 标题关键词比对；同主题仍在跟进 → 在既有事项追加时间线（必要时补 `关联项`），不新建。
   - **咨询转交付**：新建交付事项（`意图：交付`），用 `关联项` 指向原咨询事项；不要把已收口的咨询改写成任务。
   - **已出现的重复**：保留最早一条为主项，其余以 `重复` 收口并在结论行写 `关联项=<主项 id>`。
   - 同一件事既有咨询又有交付时，两事项各自收口，结论互相引用。
2. **新建事项**（派发成功且拿到 execution id / 建任务成功 / 用户提出未来计划）：
   ```bash
   ITEM="$(mktemp /tmp/wuyong-item.XXXXXX.md)"   # 每次运行独立临时文件，避免并发覆盖
   # 写入正文到 "$ITEM"
   hifox docs document create --name "<id> · <主题> · <标题>" \
     --shared <文档集 id> --parent <状态文件夹 id> \
     --content-file "$ITEM" --output json
   ```
3. **追加时间线 / 更新状态与最近核对**：先 `view`，在正文追加或改对应行，再整文替换：
   ```bash
   ITEM="$(mktemp /tmp/wuyong-item.XXXXXX.md)"   # 同一 run 内复用，不要固定路径
   # 写入合并后的正文到 "$ITEM"
   hifox docs document edit <事项文档 id> --shared <文档集 id> \
     --content-file "$ITEM" --yes --output json
   ```
4. **状态变更**：移动文档，不改名（收口除外）：
   ```bash
   hifox docs move <事项文档 id> --shared <文档集 id> --to-shared <文档集 id> \
     --parent <目标状态文件夹 id> --yes --output json
   ```
5. **收口**（仅在完成对外转述后）：追加 `结论：<verdict> · …` → 改名追加 ` · <verdict>` → 移动到 `已收口/<YYYY-MM>/`（月份文件夹缺失则先 `docs folder create --name <YYYY-MM> --shared <id> --parent <已收口 id>`）。失败 / 取消在转述后先移入 `等待用户`（问重试或后续动作），用户放弃后才归档；后台巡检只追加终态结论行并标 `待转述`，不改名 / 移动 / 归档。
6. 写完回读核验：目标文件夹列表里出现该事项、原文件夹列表里消失、收口名与正文 verdict 一致。

## 8. 并发纪律

- **单写者（语义）**：只有创建该事项的会话改请求、结论与状态；其他会话只读。**写入例外只有两个**：① 后台巡检——只追加终态结论行、`状态` 与 `最近核对`，不改请求与既有结论，且跳过 5 分钟内刚被前台更新过的事项；② 接管——见下条。平台保证同会话 run 串行，因此同一事项不会被同一会话的两个 run 同时写。
- **无共享索引**：任何时候都不创建/重写「总台账」「当前状态」这类共享文档；跨会话可见性由文件夹列表天然提供（每份文档的创建/移动在服务端是原子操作）。
- **写前重读**：改任何事项前先 `view`，比对 `最近核对` 与时间线末行；任一与上次读取不一致说明被改过（前台 / 巡检），先合并再写（同一事项同时被两个会话写时，后写者覆盖，影响仅限该条，服务端版本快照可回溯）。
- **接管例外**：仅当平台查询显示该项已终态（workflow `status=completed|failed|cancelled`，或任务已关闭）且事项正文最后更新超过 10 分钟时，新会话才可接管一次——先重读正文，再追加结论并移动；仍非终态的事项只读汇报，绝不提前移动或改写。
- **文件夹竞态**：先 list 后 create；并发建出同名文件夹时用第一个，不删除重复项。
- **临时文件竞态**：同一台机器上的并发 run 共享 `/tmp`；写正文 / 摘要一律用 `mktemp`（或带事项 id / run id 的唯一后缀），绝不用固定路径，避免两个 run 互相覆盖后写错文档或发错消息。
- **绝不删除文件夹**（级联删子文档）；删事项需用户明确要求。

## 9. 容量与清理

- 常驻成本 = 3 个未完结文件夹的列表 + 未完结事项正文，与历史长度无关。
- 未完结事项 >20：在回复里提示积压（列 id + 标题），建议收口或转任务，不静默丢弃、不自动归档未完成项。
- `等待用户` 项超过 7 天：用户下次交互时提醒一次「仍等你确认」；超过 30 天且仍无答复，建议取消收口（由用户确认）。
- `计划` 项超过 90 天未动：提示用户确认「还要不要做」，由用户决定执行、延期或取消收口。
- `已收口` 默认永久保留（按自然月归档）；只有用户明确要求才 prune，且删除前列清单确认。超过 12 个月的月份文件夹：在用户问历史或做容量提醒时**提示可 prune**，默认不删。

## 10. 失败降级

- 文档集解析失败：本会话不写入，回复中注明「记忆不可用（原因）」；仍完成当前请求。实例 / 状态文件夹**不存在不是失败**，按 §5 自举。
- `canWrite=false`：只读恢复上下文，不写；明确告知用户台账无写权限。
- 平台查询失败：事项时间线追加「查询失败（时间）」，下一轮重试，不据此宣布完成或失败；**查询失败 ≠ 对象不存在**（先重试一次，再按异常表判断）。
- 台账丢失 / 损坏时的只读兜底（不凭猜测补账）：
  - `hifox workflow logs list --workflow <workflow-id> --space "<Space>" --limit 200 --filter '{"startDate":"<ISO 时间>"}' --output json`（每行含 `executionId` / `status` / `createdAt`；`nextCursor` 翻页）；
  - `hifox agent list --output json` 取同层级吴用 id → `hifox run list --agent <自己的 id> --limit 200 --output json`（服务端最多返回最近 200 条，含 chat 运行）→ `hifox run view <run-id> --output json` 读顶层 `status` 与 `result.output`。

## 11. 边界

- 平台没有内建跨会话 / 按 agent 的记忆：每轮上下文靠执行机上的运行时会话续接；运行工作目录默认 7 天被 GC，且不存在按 agent 隔离的持久目录（同一用户的所有 agent 共享真实 `$HOME`）。**本机文件不能当记忆**。
- 会话内补召回平台消息（不跨 `/new`）：`hifox run view $HIFOX_RUN_ID --field chatSessionId` → `hifox chat messages <chatSessionId> --limit 100 --output json`；查不到不等于「没做过」。
- **对外转述遵守 instructions §5**：台账正文里的 agent / workflow / execution id / 任务号 / Space / 术语都不得出现在飞书输出；对用户只说结论与下一步。
- 平台内建的 omp-harness 记忆是按仓库的排障摘要（跨 agent 共享），与调度工作无关，不要依赖。
- **夜间自省文档只读**：`Agents/裴宣/`（staging 为 `裴宣 (staging)`）下的日记、改进项与总览由反思者单写；吴用只读总览、只在本台账记决策，不移 / 不改反思者文档。
- **对话之外由后台巡检兜底**：automation `wuyong-ledger-sweep` 每 30 分钟按同一套真值规则对账「进行中」事项（终态只标 `待转述`、不归档；异常标注并私聊上报），不重派、不碰「等待用户」「计划」。它是尽力而为的加速器：可能失败、延迟或与前台会话并发；任何回答仍以本轮查询为准，只报「最近核对」时间，不声称实时监控。
