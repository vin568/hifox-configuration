# 只读调研

只要答案、不要改动的作业用：查明现状、定位根因、评估影响面、比较方案。产物是报告，不是 diff。

## 阶段

1. **问题边界** {#question}
   写清要回答什么、明确不回答什么。边界不清先一次问清，不扩成无目的的全仓扫描。

2. **定位入口** {#locate}
   从用户描述里的界面用词、报错文本、接口路径、符号名、配置键、日志片段出发，用中英文与代码标识符多关键词搜索；不要按印象猜文件。

3. **只读采集** {#collect}
   允许读文件、看 diff、查历史、读配置与既有测试；不创建、不修改、不删除文件，不跑会写工作树的构建与测试。需要运行才能确认的结论，标注「需要运行验证」，交给下一步或交回主控。

4. **沿数据流追到底** {#trace}
   从入口沿调用链追到数据落点：谁产生、谁消费、状态怎么迁移、失败与重试怎么走。改动面涉及多个组件时，逐个组件给出结论。

5. **证据分级** {#evidence}
   把结论分为：已确认事实（有文件与符号证据）、推测、未发现证据、需要运行验证。注释与文档不能单独作为强事实；代码、需求、文档冲突时列出冲突，不替任何一方裁决。

6. **影响面** {#impact}
   列出受影响的行为、调用方、共享契约、边界条件与回归范围；明确未覆盖的部分。

7. **结论** {#conclude}
   按「现状 / 根因 / 关键路径 / 影响面 / 证据 / 不确定点 / 回归范围」写进结果文件。每条结论都能指回证据；查不到就写查不到。

## 停损

停手的判据以角色契约的作业纪律为准。本方法特有的两条边界：

- 结论需要改代码才能验证 → 停手，把「要改什么、为什么、风险」交回主控。
- 任务实际要求动手改文件 → 不属于本作业法，交回主控另派。
