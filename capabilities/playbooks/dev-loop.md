# 交付改动

拿到一件「改这里 / 修这个」的作业时用。缺陷与需求共用同一条链，只有一个分叉：缺陷必须先复现再改。

## 阶段

1. **目标与验收标准** {#scope}
   把任务翻成可观察的验收标准：具体行为、入口、状态、命令或日志。写不出可观察标准就先澄清，不进入实现。记录检出里已有的未提交改动——它们不属于本任务，不覆盖、不回滚、不混入提交。

2. **只读取证** {#investigate}
   缺陷：先复现（实际行为 vs 期望行为 + 复现条件）。
   需求：摸清现状、调用链、同类实现与既有测试。
   取证按下面的作业法执行；改代码之前，关键结论必须有代码或运行证据。

[[playbook:investigate]]

3. **计划** {#plan}
   改动清单、契约变化、验证方式、回滚方式、需要裁决的项。范围扩了就记成 follow-up，不顺手做。

4. **实现** {#implement}
   只改必要文件；复用既有机制，不建第二套约定；每一行改动都能追溯到需求或验证。不回退别人的工作，不夹带无关重构与格式化。

5. **自验** {#verify}
   先跑最小相关检查，交接前跑最强相关检查；记录命令与真实输出，失败的、跳过的都写。

6. **自审** {#review}
   审查自己的 diff；有必须修复项就回到[[node:implement]]，修完重跑受影响验证再复审。
   审查步骤与产物按下面的作业法。

[[playbook:review-diff]]

7. **提交与汇报** {#deliver}
   只提交本任务实际改动的文件，显式列出路径；提交信息说明这次改了什么、为什么。按派活注入给的分支与推送规则执行——不 push 共享分支、不改写历史。
   结果写进结果文件：结论、改动清单、验证命令与输出摘要、风险与未完成项、Git 状态。

## 停损

停手的判据以角色契约的作业纪律为准，本方法不另设一套。这条链上唯一需要额外说明的是**回流**：自验或自审不过时回到[[node:implement]]，而不是把问题写进汇报交出去——只有改不动（需要授权、环境不可得、根因证伪）才结束在本轮。
