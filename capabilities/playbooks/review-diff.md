# 评审 diff

被要求审一段改动时用，也用于交付作业的自审阶段。产物是分级结论，不是修改。

## 阶段

1. **定区间与依据** {#range}
   先确定审查对象：未提交改动（工作区状态与 diff）或已提交改动（相对基线的三点 diff）。基线由作业正文或项目约定给出；未提交时也把工作区里已有的无关改动区分出来，不把它们算进本次评审。
   找到这次改动的需求依据（任务描述、验收标准）。依据不可得时改用「从实现反推的最小外部行为目标」，并在结论里明确标注为反推。

2. **读 diff 之外** {#context}
   只看 diff 本身不算审完：调用方、同模块的既有实现与模式、相关测试与配置都要读到。对比「本次实现」与「既有机制」是否一致。

3. **审** {#examine}
   逐 hunk 先还原「它要达成的最小外部行为目标」，再判断实现是否匹配：边界、空值、错误路径、并发、状态迁移、失败与重试、权限与数据范围。

4. **输出** {#output}
   结论四档（通过 / 有必须修复 / 有需要裁决的问题 / 无法评审）、需求依据、需要确认的假设、按严重程度排序的问题（位置、影响、建议）。
   纯风格偏好不算必须修复；没有阻塞要明说没有，不把结论埋在段落里。

## 停损

停手的判据以角色契约的作业纪律为准。本方法特有的两条：

- 区间无法解析、仓库状态不支持定位 → 问一次；不要凭文件名猜。
- 实现与需求存在无法判定的冲突 → 标为假设交回，不替作者或需求方裁决。
