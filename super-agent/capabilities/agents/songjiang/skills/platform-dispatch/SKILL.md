# 平台派活

远端派活不自己挑人：**一律交平台派活员朱贵（能力 key `zhugui`，本地 job）**。他读平台能力索引挑承接人、把层级转成 `--instance prod|staging`、**把用户给的原始材料写成任务正文**、经 `superctl dispatch --platform` 建单，再把任务号写进结果文件。

你的活只有三件：**转发原话、带上附件、读结果**（再加上盯进度、按用户裁决撤销）。**你不写任务正文、不拟模板**——那一步在朱贵那边，他离建单最近，也不会让用户等你的长篇整理。

**平台 ≠ hifox**：platform 指一个远端执行面——今天是 hifox（将来 sharkly、远程 ssh 主机上的 agent）。命令与目录都按 `--platform <名>` / `capabilities/platforms/<平台>/` 命名，别把 hifox 当同义词。

口径：本仓 `config/` 已声明的 agent 即全部平台能力，未声明即不存在（ADR 0017）。要新平台能力 → 提案 → 用户批准 → 加 config 声明；**声明了必须同步到 `super-agent/capabilities/platforms/<平台>/`**（ADR 0023，`superctl capabilities --check` 强制，`--check --live` 再对平台核一遍）。能力索引是你的「知道有谁」，不是派活路径——挑人是朱贵的职责。

## 一、转发原话（别整理）

信封 = 用户说的东西，原样贴进去：

```
用户原话：<原样，不要改写、不要总结、不要替他补>
层级：prod | staging | 未指定
类型：Bug | 需求 | 未指定
任务号：<可选：HF-xxxxx，补充已有任务时填>
备注：<可选：用户说的时限、已排除的方向>
```

- **不写正文、不建文件、不传 `--desc-file`**：正文是朱贵的产出（他会写进 description，运行时归档成 `briefs/<任务号>.md`，你复查读它）。
- **只整理到「哪句是需求、哪个是附件」这一层**：用户没给的信息（复现环境、期望行为）不要脑补；朱贵缺料会回「未建单 + 需要澄清」，你照那句问用户。
- **快**：一条消息进来先回一句「收到」，然后一次 `dispatch` 转发掉——别在派活前做排查或长篇整理，那会把用户晾在那儿。

## 二、附件（用户发的图、文件）

用户消息里的附件会以 `[图片 <本机路径>]` / `[文件 <本机路径>]` 出现在你的注入里。逐个作为 `--attachment <路径>` 交出去，**顺序与注入里一致，一个不漏**：

- 少了任何一张，承接人手上就没有它——这是「图片没进任务」的根因（HF-16095）。
- **不要自己编号、不要改名、不要复制文件**：原样交路径；编号与用途说明由朱贵在正文里写，运行时会按上传顺序把图片嵌到正文末尾。
- 看到的是 `[图片 img_v3_…]` 这类 **key 而不是路径** = 运行时下载失败，**不许把它当路径传给 `--attachment`**（会报读不到）；在信封备注里写一句「图未落盘，需人工补」，不要编造路径。
- 也不要把飞书消息里的临时 URL 贴进正文（会过期），平台不接受。

## 三、任务类型

平台有默认类型，默认值标错没人替你发现：HF-16095 标题写了 `[bug]`，类型却是**需求**。按用户说的判，写进信封：

- 「bug / 缺陷 / 报错 / 坏了 / 不对」→ `Bug`
- 「需求 / 希望支持 / 加个功能」→ `需求`
- 说不清 → `未指定`（朱贵按平台默认，并在结果里说明）。

类型是你唯一要做的判断，一句话，不花时间；拿不准就别填，别猜。

## 四、派活命令

```bash
# 派（唯一入口：起本地派活员 → 他写正文、建单、登记在途清单）
superctl dispatch --local --agent zhugui \
  --body "用户原话：<原样>；层级：prod|staging|未指定；类型：Bug|需求|未指定；备注：<可选>" \
  --attachment <附件路径>            # 有几个写几个，顺序与注入一致
# 用户给的是已有任务号 → 信封里写「任务号：HF-16095」，朱贵走 --update 改原单，不新建

# 读结果（JSON 的 result 路径：- 任务号 / - 链接 / - 类型 / - 承接 / - 层级 / - space / - 附件 / - 正文 / - build_notes）
```

`build_notes` 必须读：

- **「附件数对不上：上传 N，平台回 M」** → 有附件没上传成功。**不要重新建单**（会开出第二张单）：把任务号与漏掉的路径交回朱贵，让他 `--update` 补原单。
- **「正文嵌图失败」/「取任务真值失败」** → 任务已建成、附件也上传了，只是没嵌图；同样走 `--update` 重跑（幂等）。
- 一句话：**建单只一次，之后所有修补都落在同一张单上**（HF-15793 的双会话事故同源）。

朱贵建单/指派成功后会先 `report` 一句（`[触发器: agent] ...`，带任务号、承接人与链接）——收到就能回用户，不必等结果文件。

**回用户一句话带链接**（结果文件的 `- 链接：` 行，朱贵从 `dispatch` 的 JSON `url` 抄来的，如 `https://app.hifox.com/rayfox/task/HF-16095`）：「已建好 <类型>，跟着看：<链接>」——用户点得进去才叫交付；`build_notes` 里有失败项时补一句「图还在补」，别只说「已创建」。

## 五、复查与跟踪

- 正文归档在 `briefs/<任务号>.md`（运行时建的稳定副本，与平台一致）：要核对「这单到底写了什么」读它，不用开网页。
- 真值三件套：`hifox task view <任务号> --output json`（status / delegateStatus / agentWorkingStatus）、`hifox run list --task <任务号>`。
- 撤销：`superctl cancel --task <任务号>`（不急停）。
- 任务号由朱贵建单时**自动**写进在途清单；哨兵高频轮询清单里的平台条目，状态真变化才唤醒你（ADR 0018）。

层级语义：`prod` = 远端名不带后缀的那一份，`staging` = 带实例后缀的那一份；层级写进信封，朱贵负责落到 `--instance`，结果文件里的 `层级` 是他**实际建到**的那一层。

## 六、承接人在等用户回答

承接人把问题问在任务对话里，会话置 `waiting_human_reply`（等你回答）或 `waiting_human_review`（等你验收）后结束回合——哨兵会点名这两态（变化时与首见都在内），并给出带平台的 `answer` 命令。

- **回答位置固定是任务对话，不是任务评论**，也不需要用户每次强调。用户回话后：

  ```bash
  superctl answer --platform hifox --task HF-xxxxx --text "<用户原话>"          # 多行用 --text-file
  ```

  它选活着的会话（`sessionStatus.top.sessionId`，没有就回落任务主会话 `chatSessionId`），以 CLI 的人工身份把消息写进那条对话（`POST /rest/v1/chat/sessions/<id>/messages`），平台记成用户的一轮并唤醒承接人。返回 `message_id` / `run_id` / `queued`（`queued=true` 表示排在承接人当前回合之后）。
- **不是派活**：不走 `dispatch`（不建单、不走 `--update` 改正文——改正文是改需求不是回答）。
- **不许写评论**：`hifox task comment` 不产生承接人的回合，写在那里等于没答；减少信息量时也不要「评论 + 对话」双写。
- **不许自己拼 curl、不许读 `~/.hifox/config.yml` 的 token**：`answer` 用 CLI 自带登录身份；手工拼 REST 等于让主控读凭证（硬禁区）。
- 用户的回答里带「在对话中回复」这类前缀时剥掉再投——那是给编排者的位置说明，不是回答内容；他中途更正（先「开工」后「执行」）只投最后一条。
- 投完把 `message_id` 与投递前状态记进台账，回用户一句；承接人被唤醒后状态会变 `working`，哨兵再报一次时按常规跟踪。

**派活员自己也是本地的活**：他起来、跑完、写结果——你读文件，别让他常驻（干完 `superctl cancel --agent zhugui-<时刻>`，或让他自己退出）。
