# ADR 0038：飞书群的服务边界与发送者身份

宋江在私聊之外进入多个群后，群消息的准入与回复语义原先只有一条「@bot 即放行」：任何群成员 @ 一次就能让它像私聊一样追问、派活、回帖；`any_message_groups` 更是把整个群的所有消息都放进来。这既扩大了任务来源，也让「不该回答的内容」有了出口。2026-11-22 的决策把群从「私聊的另一个入口」改成「受限的任务面」。

**决策：**

- **准入只看两件事：真人与 @bot**。`sender_type=bot` 的消息一律丢弃（不区分会话）；群消息要求发送者是真人且 @ 了 bot。`any_message_groups` 删除（配置里残留会直接报错并给出说明），代答群开关保留但当前为空——开启等于显式允许他人 @ 主人触发代答。
- **发送者身份位（owner / member）**。`allowed_users` 里的发送者在群里是「主人」，其余 @bot 的成员是「成员」。身份位进注入信封，回复能做/不能做什么由它决定，不由准入决定。
- **主人触发完整互动**：推断、派活、进度、结果；群里先加表情回执，结论回在触发话题/消息下。
- **成员只有一条出口**：明确询问**本群/本话题在途任务**的进度时回一句。其余内容静默——不接活、不反问、不派发、不发回执，也不顺手报一遍所有任务进度。任务不是本群发起的，不回（防跨群泄露）。
- **单主控会话不变**。所有群/话题仍注入同一个主控会话，靠注入里的来源标识区分；本批不做每群/每话题独立会话。
- **急停语义不变**：群/代答消息是 machine-class，急停期间静默丢弃；只有白名单私聊能进、能解除急停。
- **对外只聊任务相关**：群里的回复不出现内部 agent、workflow、Space、执行编号、台账与工具术语。

**Considered Options：**

- **保留 any_message_groups**：拒。它等于任何人任何消息都能触发，与「只由主人触发」冲突；真需要免 @ 时再按话题做显式粘性。
- **成员也接活**：拒。任务与信息会跨人扩散，且当前没有「谁被授权代表主人」的模型。
- **按群配置模式（只读/咨询/全权）**：拒。配置面变大，当前只有一个问题：这条消息能不能得到回复。
- **每群独立主控会话**：拒（本批）。框架只有一条主控会话，换脑/上下文测量/台账都按单会话设计；串群风险用来源标识与成员出口规则压住。

**Consequences：**

- `internal/admission` 从「放行/代答」二元结果改为 `Decision{Admit, ProxyReply, Owner}`；所有调用点必须显式处理身份位。
- 群成员 @bot 的消息也会注入并消耗一轮上下文；靠手册纪律与 `group_tasks` 清单把它限制在「只答本群进度」。
- `any_message_groups` 下线是破坏性配置变更：`config.Load` 报错并指向本条规则，不静默忽略。
- 机器人互触发被关闭；跨 bot 协作继续走 herdr / direct，不走飞书事件。

## 2026-11-27 修订：成员进度回答可带平台任务短 id 与链接

成员询问本群/本话题在途任务进度时，回答可以带平台任务的短 id 与可点击链接（`[HF-16434](url)`，ADR 0046）；这是任务相关信息，不属于内部术语。仍然只答进度、只列来源匹配的任务；不出现内部 agent、workflow、Space、台账术语、机器 key 与本地作业 key。作业话题在群里对成员可见，因此话题内的主人消息同样不写机器 key、agent 名与 workflow。
