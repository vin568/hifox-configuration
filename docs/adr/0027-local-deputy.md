# ADR 0027：本地副手石秀——主控的活只有两个去向

> **部分推翻（2026-11-20）**：用户决定本地 job agent 不得编辑本仓 `/Users/vin/code/apifox/hifox-configuration`，石秀收缩为**只读调研员**（不创建/修改/删除任何文件，不跑写工作树的构建与脚本，不做 git 写操作）；「调研→改动」连续链路由后续接入的**专用编辑 agent** 承接，接入前编辑类活由主控上报用户、无人执行。原「一个副手不按读/写分类」与「并发定 1（同工作树写冲突）」两条随之失效：只读无写冲突，`maxConcurrent` 现为 5。手册、能力描述、`local-agents` / `direct-tiers` 技能同步收紧；结果骨架去掉「改动」字段（只读作业恒无改动）。**只读只在提示词里约束，不上机械闸门**（用户 2026-11-20 决定）：作业 agent 仍以本机 `tools.approvalMode=yolo` 启动，`--tools` 白名单会连 `bash` 只读查询一起砍掉，收益不值。

宋江的操作手册定了一条硬边界：只做读、写、派、判四类轻动作，预期超过十秒或要产出内容的工作一律下发。2026-11-19 的实际运行暴露这条边界没被真正兜住：用户让宋江「排查/调研」时，他会用一长串只读命令自己查完，或者用自己工具箱里的子任务把活干完。旧措辞「只读命令自由跑」只限制命令副作用、没限制目的，「加上你自己的工具箱」也没界定用途——两条都是合法的绕道。当天已把「排查、调研、根因分析、方案对比、资料搜集、写报告」明确归为「产出内容、一律下发」，并写明工具箱只服务编排。

措辞修正后，缺口变成结构性的。主控的活只有两个去处：平台/产品交付经朱贵交平台专家；**其余本机活没有承接人**——朱贵不读代码、平台专家看不到本机与本仓。于是「写得对不对」之外还有「有没有人接」，后者不解决，宋江只剩自己干或拒绝用户两条路。

**决策：**

- **新增本地副手石秀（`shixiu`）**：`role: job`、`workspace: jobs`、`kind: omp`、`maxConcurrent: 1`，按能力注册表目录即声明（ADR 0021）接入，不新增 role、不改运行时。**并发定 1**：副手在同一个工作树里改文件，两个实例同时改同仓会互相覆盖、也会争抢 `go build`/`go test` 的构建缓存与端口；本地活本就串行，串行不损失什么。
- **一个副手，不按「读/写」再分类**：调研、排查、根因与方案对比、读代码找事实，与写脚本、改本仓配置/文档/技能/运行时代码、跑构建测试、整理数据与文件，是同一个人。**「先调研再动手」是一条连续链路**，拆成两个人会多一次交接、丢掉上下文，还会在边界上留缝（两边都觉得该对方接）。
- **主控的判据只有一问**：是不是平台/产品交付——是 → 原话转朱贵（类型按 Bug / 需求 / 未指定）；不是 → 一律派石秀。不分类、不预判、不「看起来只是查一下」自己上。
- **石秀的边界（手册与能力描述里写死）**：
  - 改动留在工作树，**不自行 commit / push**，不碰本仓以外的仓库与远端；
  - **不动运行时**（不重编、不重启、不启停 `superctl` / 注入器 / serve，不关别人的 pane）：故障定位与时序改动分开——进程出问题只做只读定位、处置交回用户；用户明确要求改运行时代码时按普通开发任务改，改动留在工作树，绝不自行重编或重启；
  - **不派活、不对外**（不调 `superctl dispatch`、不碰在途清单与作业台账、不给用户或平台发消息）；
  - **不做产品交付与发布部署**（xwing 产品仓库的修复与需求归平台专家，只读现有本地材料取上下文，不 clone、不改产品仓库；不碰 `environments/` 的实例）；
  - 不碰密钥凭证与机器标识。
- **需批准的动作先停手**：删除或覆盖用户已有文件与数据、装软件、升级工具链、改全局配置、本仓外或系统级变更、任何「做错不好回滚」的动作——写进结果文件的「需要你决定」，由主控问用户，批准后另派一次。**批准回路是显式的，不靠模型自觉。**
- **产物固定形状**：`结论 / 状态 / 改动 / 验证 / 事实与依据 / 做了什么 / 需要你决定 / 未决与风险`，只回文件路径；验证写清跑了什么、结果如何，跑不了要明说。

**Considered Options：**

- **拆成「只读调研副手」与「可写执行副手」**（本 ADR 起草时的第一版）：拒。判据错在「会不会写文件」，而不是「有没有人接」。调研→改动是连续链路，拆开后主控要先派甲再派乙，上下文与耐心都在交接中损耗；一旦任务性质在两单之间变化，边界处就互相推诿。副手的价值是**吞掉主控的全部非平台活**，不是把主控的分类问题再切细一层。
- **继续让主控自己做**：拒。违反主控定位；长会话被业务细节污染（ADR 0022），且调研无法并行、无法收口成可复核的证据文件。
- **全部走朱贵/平台**：拒。朱贵不读代码、不做排查（ADR 0023）；平台专家看不到本机运行时与本仓，本机问题也建不出平台任务。
- **复用蒋敬**：拒。蒋敬是 `role: retro` 的常驻复盘者，只读作业台账与运行记录、只写复盘产物；塞进通用执行会破坏复盘产物的可信边界，也让常驻会话承担任意题目的上下文。
- **给主控加一个 research 技能或直连白名单脚本**：拒。技能只是把「亲自干活」包装得更顺手，执行者没变；白名单只能跑预设固定动作，写新脚本、改配置的活它接不住。
- **新增 `role: deputy`**：拒。`role: job` 已覆盖按需拉起、并发上限、结果文件与在途登记，多一个 role 只多分支。
- **让石秀自己 commit/push**：拒。提交是用户的裁决点（本仓与子模块指针流程有明确规矩），副手越权提交会抹掉「谁的改动」这一层。

**Consequences：**

- **本机活有归属了**：主控的「不自己干活」从原则变成可执行的分派，判据一问定死，没有第三类。
- **多一跳与一次上下文交接**：主控要把背景与验收写清；写得含糊会得到一份泛泛的产物。
- **工作树里会出现未提交的改动**：这是特性不是缺陷——用户与主控都能看到、能审；提交仍走既有流程。
- **副手不常驻**：派完即用、干完 `superctl cancel --agent` 收掉；忘收口占并发额度，靠主控巡检盯。
- **能力索引一句话可辨**：描述里直接写「本机与本仓里平台专家接不到的活全归他」，避免主控按名字猜能力。
- **直连三级的执行者换人**：主控只行使第 1 级（只读、编排核对）；第 2 级（白名单脚本）与第 3 级（白名单外变更）变成**派给副手时的授权分级**——主控判断该不该做、要不要先问用户，执行由副手在任务授权下完成。ADR 0019 的权限闭集与硬禁区不变，变的是谁的手在执行。副作用：主控不再需要为每件本机变更亲自记账到命令级，台账记的是「派了什么、批了什么」。
- **主控的工具箱仍是最大风险面**：本 ADR 只保证「有承接人」，屏蔽不了子任务与研究技能。真正的闸门是复盘抽查（蒋敬的越界点名），应当在每日复盘里持续盯这一项。
