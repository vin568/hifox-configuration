# 急停与换脑：白名单私聊 `/halt` 后同 pane 换新会话，首条注入急停意图

用户发现主控在跑错误指令时的现状是**没有止损手段**：注入通道按到达顺序进会话，当前回合与排队中的指令都拦不住，错误指令会一条条执行完；事后补救（发一条「停」）只是又一条排队消息，排在错误指令之后生效。要「及时止损」，需要的是一道秒级、用户本人按压、且按下去之后不残留错误上下文的闸门——错误上下文留着，新回合仍会被它误导。

**决策：**

- **入口 = 飞书白名单私聊 `/halt`**，本机 `superctl halt` 等价（运行时停机或用户人在终端时用）。只有白名单私聊进得来，见下「注入闸门」。
- **换脑的「停 → 起 → 灌首条」与并发 `ensure` 互斥**（2026-11-26 修订，框架 ADR 0019）：`boot.Fresh` 与 `boot.Ensure` 共用 `state/prime.lock`。否则后台 tick 会在「已停、未起」的窗口里用普通手册起一个主控，急停/换脑的附加意图丢失，而换脑只比较会话路径、仍会报成功。
- **闸门动作 = 换脑（Fresh Session）**：同一 pane 停掉主控进程，按实测出来的阶梯走——先 `esc` 中断回合，再提交 `/exit`（omp 的退出是 slash 命令；`ctrl+d` 在草稿非空时只删字符，TUI 自己会提示），轮询 agent 列表直到名字消失；`/exit` 不生效再退 `ctrl+d`，仍不行才关 pane（workspace 随最后一个 pane 消失，由 `ensure` 重建）。实机实测：运行中的主控从按停到新会话就绪 4–5 秒。每轮次独立 session 目录留档，旧会话全文可查、不被覆盖。
- **首条注入 = 急停意图**：机器真值（在途清单）+ 旧会话留档路径 + 逐件请示是否停 + 用户回话前不自动继续。会话被整体换掉、旧上下文不可读，所以恢复动作必须由这条注入自解释：主控拿到的不是「接着干」，而是「盘点并请示」。
- **失败阶梯**（逐级退，永不硬杀进程）：停不掉 → 关 pane；workspace 随之消失 → 由幂等引导（`ensure`）重建拓扑并起新会话；再失败 → 上报用户，停在这里。不 `kill -9`：进程被硬杀会留下外部可见的半成品（租约、pane 状态、在途登记），失败阶梯的每一步都是可解释、可重放的拓扑操作。
- **两段回执**：运行时立刻回一段机器清单（在途条目、本轮次标识、留档路径），经统一对外通道投递——这是秒级、不依赖模型的一段；业务解释（这些在途件分别是什么、建议怎么处置）由换脑后的主控首条注入给出。用户先看到「已停」，随后看到「停的是什么」。
- **注入闸门 = state 目录下的 halt 文件**，按来源分流：巡检 tick、云端哨兵、状态变化事件、放行群消息一律静默丢弃；白名单私聊与运行时的急停意图注入放行；outbox 投递照常（已产生的回帖该发就发，闸门只管注入方向）。
- **解除不需要额外动作**：用户下一句私聊即恢复（急停是用户按的，也由用户的第一句话结束）。静默期内哨兵照跑、状态变化照记，恢复时一次性补交；`superctl resume` 只是离线兜底（用户不在飞书而想放行时用），不是常规路径。
- **撤销不等于急停**：要停的是「某件正在跑的工作」，用 `superctl cancel`——云端走 run 列表 → 取消 run，本地关对应 pane。急停是停主控自己，两者不能互相代劳；把撤销混进急停会让「停一件」变成「停全部重启」。

**Considered Options：**

- **`esc` 打断当前回合再注入急停意图**：拒。打断只回收当前回合，omp 的排队消息队列（queuedMessages）会继续把错误指令执行完，急停意图排在它们后面——正是要避免的「止损晚一步」。
- **急停自动级联取消云端 run**：拒。不可回滚：run 已产生的分支、提交、预览环境无法撤销，而「哪些该留、哪些该弃」是用户的业务裁决。级联取消属撤销，由主控按用户逐件裁决执行（见 `superctl cancel`）。
- **手动「继续」解除**：拒。遗忘即静默失效——闸门挂着、哨兵照跑、用户以为一切正常，实际注入全被丢掉。解除锚在「用户自然会说的一句话」上，比锚在一个专门动作上可靠。
- **关 pane 换新 pane**：拒。破坏幂等引导的拓扑假设（拓扑由 workspace/pane 结构承载，外部观察者按结构寻址）；关 pane 还会连带丢 workspace，代价远大于换会话。

**Consequences：**

- 急停丢掉主控会话上下文：跨会话记忆只剩作业台账与在途清单——这两件必须随时可读、随时可信，否则急停之后主控无法自恢复。
- 会话留档目录随急停次数增长（与换脑轮换共用同一套轮次目录），需要归档或清理策略跟上。
- 闸门是运行时状态文件，不是 CLI 参数：运行时重启后闸门状态需与磁盘一致（进程内开关会导致重启即静默失效）。
