# 上下文三件事：注入只带增量、轮换复用换脑、`/new` 人工清空

> 2026-11-19 补充（ADR 0030）：轮换触发已从会话字节数扩展为「provider prompt token / 模型窗口」的保留区策略；字节数降级为测量不可用时的兜底。本文的换脑管道与职责边界不变。

主控是长会话：实测单会话已到 1.79MB / 441 条消息，且无任何压缩记录。注入只增不减——巡检每 10 分钟一条，即使一件在途工作都没有；每条注入都重复同一套样板、同一份手册口径，增量信息淹没在重复里。仓库里也不存在任何上下文预算概念：没有阈值、没有度量、没有轮换动作，只有「会话越来越长」这一个事实持续变坏。三件事要一起定：注入时少写、超阈值时换掉、用户想清时能立刻清。

**决策：**

- **注入卫生（注入源自己收敛）**：巡检注入只在三源任一非空时发——活跃区台账文件数、在途清单条数、jobs workspace 活动 agent 数；全空只记日志、不注入。每条注入只带增量，样板（手册口径、路径约定、模板）只在首条 prime 里出现一次。省的是 token，保的是「没有新信息就不占注意力」。
- **轮换 = 复用换脑管道**：触发条件是会话文件字节数超阈值且主控 idle（在回合中间换会话会砍掉正在干的工作）。换脑是停进程 + 起新会话 + 首条注入，轮换与急停共用同一条管道、同一套轮次留档目录，不另建机制。
- **人工清空 = `/new`**（飞书私聊）：语义与轮换完全相同，只是不等阈值、由用户当场决定。用户想清就清，不必先让上下文涨到难看。
- **职责边界**：运行时判定 + 执行（字节数、idle、停起会话都是它的活，可观测可测），交接材料也由运行时从机器真值生成（在途清单 + 活跃区台账，落 `handoff.md` 给新会话首读）——主控自判「我该不该换脑」既看不到自己的字节数，也没有执行换脑的手段，让它写交接文档只会多一个「还没写就换了」的失败模式。
- **会话留档每轮次独立 session 目录**：轮换、急停、人工清空共用同一套留档，旧会话全文可查，是换脑后唯一的现场依据。

**Considered Options：**

- **只依赖 omp 自带压缩**：拒。压缩不透明、不可测：压了什么、丢没丢在途信息，人无法核对；治理动作不应该建立在看不见的机制上。
- **主控自判轮换**：拒。不可观测——主控读不到自己的会话字节数，也没有执行换脑的手段；让它判等于让它猜。
- **只重启进程不换会话**：拒。上下文仍在，等于白重启；占用不降、误导性历史照旧，问题原样保留（换脑的语义是换会话，不是换进程）。

**Consequences：**

- 轮换成本 = 一次 prime（首条注入要重新交代环境）；省下的上下文远大于这一条的成本，但 prime 文案必须短且稳定。
- 跨会话记忆真的只剩作业台账与在途清单：任何「主控应该记得」的东西都必须先落进这两处，否则轮换即丢。
- 阈值与 idle 判定成为运行时可观测项：需要能回答「上一次轮换因为什么发生」，否则运维时无法区分「轮换太频繁」与「会话真的肥」。
