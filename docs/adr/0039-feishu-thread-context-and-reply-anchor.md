# ADR 0039：飞书话题、群上下文尾与回复锚点

飞书侧原先只支持「收一条文本 / 发一条文本」：事件里的 `thread_id` 没人读，群名与发送者名不在注入里，回帖只会 `POST /im/v1/messages` 新开一条顶楼消息。结果是在群里（尤其话题群/话题格式群）机器人无法回答「在答哪条」，每次回复还可能开出一个新话题；模型也没有群上下文，只能像私聊一样反问。

**决策：**

- **入站读 `thread_id` 与 `sender_type`**。`thread_id` 进事件视图、注入载荷与来源日志；`sender_type` 参与准入（bot 丢弃）。话题消息在飞书里仍是 `chat_type=group`，不要按 `chat_type=topic` 处理。
- **注入信封带来源与身份**：群名、发送者显示名、话题 id、触发消息 id、引用块的发送者名；群消息再附「群上下文尾」。
- **群增强只对群消息**：群名、发送者名、上下文尾都只在群/话题信封里出现，私聊保持原形态（也省两次 IM 查询）。来源日志与表情回执**在注入闸门放行且注入成功之后**才发生：急停拦下的消息不留可见回执，也不记成“曾经触发过”。
- **群上下文尾固定小预算**：最近 6 条，每条 150 rune；话题消息取 `container_id_type=thread`，普通群取 `chat`（话题群/普通群的 chat 容器只回根消息，这是平台契约）；总预算 2s，失败只写一句降级说明，绝不阻断注入。更深历史由主控按需 `history`。
- **名字解析只走 IM 只读接口**：群名 `GET /im/v1/chats/:id`，成员名 `GET /im/v1/chats/:id/members`；按 chat 缓存 10 分钟。当前应用没有联系人姓名权限（`contact/v3/users` 只回 open_id/union_id），不申请该 scope，也不拿它当兜底；拿不到名字就回退到 open_id。
- **回帖优先挂回复锚点**：outbox 条目新增 `reply_to`；`superctl reply --reply-to <om_…>` 调 `POST /im/v1/messages/:message_id/reply`。目标本身是话题消息时平台自动落进话题；普通群是平铺引用。锚点已撤回/不存在（230110）时退回普通发送并记日志，避免丢回帖。私聊回复维持普通发送。
- **`reply --admin`**：直接发到配置的 `admin_chat_id`，让主控在群里遇到需要拍板的事时私聊主人，不必把会话 id 写进上下文。它与 `--reply-to` 互斥：回复接口的落点由锚点消息决定，两个 flag 同时给会把本该私聊的内容发到锚点所在的群/话题。
- **`history --thread <omt_…>`**：用 `container_id_type=thread` 读话题内全部消息；话题容器不支持时间范围，`--since` 直接报错。`--chat` 行为不变（话题群只返回根消息）。
- **表情回执是尽力而为**：主人群消息先加一个 `OK` 表情，替代文字“收到”；应用没有消息表情回复权限时静默跳过。成员消息不回执。

**Considered Options：**

- **所有群回复都强制开话题**：拒。会改变群的既有形态；只在触发消息本身属于话题时跟随。
- **正文按语义位置嵌图**：拒（本批）。位置式占位要求派活员预知语义位置，错位比文末固定小节更糟；改为校验「嵌入图片数 = 图片附件数」。
- **用 contact scope 做全量姓名解析**：拒。多一个权限面，且 IM 成员列表已覆盖群/私聊场景；反查（hifox → 飞书）需要枚举所有群，不做。
- **每条群消息都拉更长历史**：拒。注入卫生（ADR 0022）要求增量小；6 条 + 按需 `history` 足够支撑推断。

**Consequences：**

- `feishu.Config` 新增 `OriginPath`；`inject.Payload` 新增群名/发送者名/消息 id/话题 id/上下文尾/群任务清单；`outbox.Entry` 新增 `reply_to`。
- `messageReader` 新增 `ListThread`；`historyList` 的 chat 列表仍支持时间窗口。
- 群消息注入多一次历史 API 与名字查询（有缓存与 2s 超时），换取更少的反问。
- 回帖锚点是可选字段：旧 outbox 条目没有锚点，按原路径投递。

## 2026-11-25 修订：私聊话题也要锚点

「私聊回复维持普通发送」只对**无话题的私聊**成立。飞书 p2p 会话里同样能开出话题（`chat_type=p2p` 且 `thread_id` 非空），这类消息原先被渲染成「私聊」且不带「消息 <id>」行，主控按私聊规矩回帖，回复平铺在主会话——实测同一话题里两次回复都飘走，outbox 294 条里 `reply_to` 非空仅 6 条。

渲染规则由框架侧收口（框架 ADR 0012）：带 thread 的消息无论 `chat_type` 都给「话题 <id>」「消息 <id>」两行，标签为「话题」。`kindOf` 不动：这类消息的 `Payload.Kind` 仍是 `dm`，不触发群名/成员名/上下文尾/成员任务清单/群回执那一族群语义。因此本 ADR 的「群增强只对群消息」与「私聊回复维持普通发送」在**无话题私聊**上保持原样，区分维度从 chat 类型变成「有没有 thread」。

## 2026-11-27 修订：按作业懒建话题

「所有群回复都强制开话题」仍然拒绝；新增窄例外（ADR 0046）：第一条带作业 key 且带显式锚点（`--reply-to`）的回帖，用 `reply_in_thread=true` 建出该作业的话题，后续主动更新投进话题。显式 `--reply-to` 永远优先——用户在主区提问就在主区回答；`--admin` 与无锚点消息不建话题；建话题失败 fail-open，退回普通发送。
