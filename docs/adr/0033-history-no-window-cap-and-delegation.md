# ADR 0033：历史查询取消窗口与单页上限，繁重查询外派

ADR 0032 把 `history` 收敛成「`--limit` 1..50、`--since` ≤168h、只拉一页」。2026-11-20 用户指出这组
限制的事实归属搞错了：

- 50 条是飞书**单页**上限，不是可查询总量；
- 168h 是本地自设窗口，平台按起止时间查询，能往更早要；
- 只拉一页意味着 7 天以内超过 50 条也拿不全。

结果是需要回看历史时工具反而无能为力。同时用户明确主控的优先级是**高性能、快速响应**：查询本身
繁重时应该外派，而不是让主控自己搬运大段历史。

**决策：**

- **取消 `--limit` 的 50 上限，改为自动翻页**。`HistoryPageSize=50` 是飞书的单页上限，
  `historyList` 按 `page_token` 逐页拉取，直到凑够 `--limit` 或平台没有更多；`page_token` 为空或
  原地踏步立即停止（防脏数据死循环）。页脚区分「已到 `--limit`」与「翻到尽头」，不虚报还有更多。
- **`--limit` 就是资源预算**：翻页只为凑够 `--limit`，凑够立即停，不预先拉满窗口；每页只请求剩余条数
  （上限 50），不超额多取。默认值仍是 20 条 / 24h 一页，零参数查询的成本与改动前一致。
- **取消 `--since` 的 168h 上限**，只保留 `>0`：窗口多长由调用者决定，本地不再替平台设产品限制。
  不提供「不限起点」：飞书对省略 `start_time` 的默认范围没有本地可依赖的契约，显式窗口更可预期。
- **单次查询预算 10s → 60s**：多页请求需要时间；仍受 `ctx` 取消与平台超时约束。
- **繁重查询外派**。大 `--limit`、长窗口或大范围回溯由主控派给本地副手（石秀）执行，主控只读结论
  文件。主控上下文与响应速度是稀缺资源；`history` 自己不再假装能同时满足「无限量」与「快」。

**Considered Options：**

- **保留 50 上限、让用户分段查**：拒。用户拿不到 `page_token`，分段只能靠调大 `--limit`，等于没解决。
- **换一个新的拍脑袋上限（如 1000）**：拒。真实边界是输出体积与等待时间，应由调用方和超时决定；
  调用方给多少 `--limit` 就取多少，不多取一条。主控侧再靠外派纪律约束上下文占用。
- **默认翻到窗口尽头**：拒。那才是真正的资源浪费：一次查询把窗口内所有消息都拉一遍。
  默认仍以 `--limit` 为界，翻页只补足差额。
- **`--since 0` 表示不限起点**：拒。平台省略 `start_time` 时的默认范围没有稳定契约，本地不猜。

**Consequences：**

- `internal/feishu` 的 `messageLister` 增加 `pageSize`/`pageToken` 入参与 `nextToken` 出参；
  `sdkMessageReader.List` 透传 `page_token` 并返回下一页 token；翻页与时间正序反转都在 `historyList`。
- `superctl history` 的参数校验、帮助文本与 README 同步；`cmd/superctl` 不再引用
  `HistoryMaxLimit` / `HistoryMaxSince`。
- ADR 0032 中「列表只取一页」「`--limit` 1..50」「`--since` ≤168h」三条以本 ADR 为准；0032 原文保留。
- 主控手册的直连纪律补一条：繁重历史查询外派给本地调研员（石秀，只读），主控只读结论。
