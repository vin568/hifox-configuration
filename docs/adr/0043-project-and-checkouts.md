# ADR 0043：项目与检出——代码从哪来，由主节点说了算

本地与执行节点的 job agent 至今没有「项目」概念：平台侧靠 `config/<集合>/agents/<key>/agent.yaml` 的 `repositories`（部署面事实，由 x-deploy 同步），本机与节点侧靠手册里写死的绝对路径（`/Users/vin/code/apifox/sharkly`）。三台节点的 `work_dir` 全是家目录、note 写着「仓库未检出」，手册路径在它们上面根本不成立。同时 `nodes/<key>.yaml` 的 `instance_root` 要求每台机器都有一份本仓检出，而这只是为了让技能与直连脚本可用——实例代码改一处，就要逐台同步。

用户要两种用法：**交付类作业**从仓库取代码、在隔离工作区里做；**排查与共同开发**直接在机器上已有的项目目录里做，用户自己看效果、自己决定何时合并。两者都要能派到本机或执行节点。

**决策：**

- **三层词汇，机器无关与机器相关分开**：项目（仓库身份 + 基线分支，机器无关）→ 检出（某台机器上的工作副本路径）→ 作业工作区（从检出派生的 linked worktree）。术语见 `GLOSSARY.md`「代码库」节。
- **项目声明 `capabilities/projects/<key>.yaml`**：`repo`（可缺省，缺省即目录型项目）、`aliases`（同仓别名）、`base`（缺省基线）。全局 key，不与配置集合分区——项目识别的是硬盘上的一块代码，与部署到哪个 Space 无关。
- **检出表 `capabilities/nodes/<key>/checkouts.yaml`**：机器上的路径只写在机器侧（裸映射 `项目: 绝对路径`）。本机的项目挂在本机节点下。这是「路径属于机器」的直接落法：加一台机器只改它自己的目录，不动项目文件。
- **能力清单 `agents/<key>/projects.yaml`**：该能力能碰哪些项目；缺省为空（不能用项目）。
- **`--project` 默认只读**：检出路径注入 prompt 并作为 pane cwd；agent 不写文件、不切分支。写作业必须显式二选一：
  - `--in-place`：原地写。派活前 `git status --porcelain`，脏则拒绝并返回原因，主控问用户，用户同意后带 `--allow-dirty` 重派（一次性，不落状态）。允许后 agent 禁止 `add/commit/stash/clean/reset/checkout`，改动留给用户。
  - `--worktree <作业名>`：交付走作业工作区形态。派活只**计划**工作区（路径、分支、基线写进角色契约），由 agent 在自己的那轮里调 `direct/worktree add --repo <检出> --name <作业名>` 实际切出——子模块要从远端克隆，派活不该阻塞在这上面。
- **非 git 目录**：只读可用；写作业要求用户先把目录变成 git 仓库（提示，不自动 `git init`），转成后仍需过脏门禁。
- **防重复键含项目**：同一能力 + 同一项目 + 同一正文 + 同一附件组才算「同一请求」。项目是派活语的一部分——同一句「跑一遍测试」打到两个检出是两个作业，判重会误杀；同一项目的原地写与只读仍算同一件事（写入形态是意图，不是另一个作业）。
- **`--auto` 与原地写互斥**：自动择节点只在「该项目有检出」的候选里选，且只接只读或 worktree 形态。原地写必须显式点名位置——共享目录里用户正在写，是运行时看不见的外部状态。
- **主节点是唯一内容源**：执行节点不再需要本仓检出。派活时把该作业需要的实例文件（技能源、能力专属技能、已登记的直连脚本）复制到节点 `<state_root>/jobs/<run>/material/`，技能发现根与直连脚本目录都指向它；收口即清（cancel、交接后的旧轮、派活失败回滚各清一次），节点上不留跨作业的副本。`instance_root` 从节点声明里删除，相关映射与校验一并退场（机制细节见框架 ADR 0011）。
- **工作区助手沿用 `worktree` 这个名字**：参数扩成 `add --repo <检出绝对路径> --name <作业名> [--branch] [--base] [--no-submodules]`（按检出绝对路径解析，不查项目表——脚本在节点物料目录里跑，那里没有注册表），描述改为「项目工作区管理」；检出里有 `.gitmodules` 时自动初始化子模块并切同名分支，`--no-submodules` 是退路。不新建 `direct/workspace`——登记表、安道全手册、直连三级文档三处都要跟着改，收益为零。
- **校验**：派活前核对项目有 `repo` 时检出的 `remote.origin.url` 命中 `repo`/`aliases`，缺路径或失配 fail closed；`npm run check` 校验静态引用、平台边界与「声明了但派不出去」的项目（没有机器检出、也没有任何能力声明它），`check:live` 逐节点 ssh 核路径与 remote（脏只报告不拦，节点不可达则跳过）。
- **`targets` 与检出按同一顺序开放**：节点先有 `checkouts.yaml` 条目，才把该节点加进相应能力的 `targets`。安道全（`andaoquan`）当前只声明本机执行面，不提前挂到三台节点上——那等于声明「可派」，而派出去必然 fail closed。
- **边界**：项目面只管本地与执行节点。平台侧的仓库绑定仍是 `agent.yaml` 的 `repositories`，由 x-deploy 的 replace-all 同步——那是部署面事实，super-agent 不读 `config/`。项目也不是路由键：不进堂/舵的主题闭集。

**Considered Options：**

- **路径写进项目文件（`checkouts: {节点: 路径}`）**：拒。每加一台机器就要改每个项目文件，且「这个项目在哪些机器上有」与「这台机器上有哪些项目」两个方向的维护成本不对等。
- **给 `nodes/<key>.yaml` 加 `checkouts:` 字段**：拒。节点声明是严格解析（`KnownFields`），加字段会让旧二进制整份失败；旁挂目录对旧二进制不可见，滚动升级安全。
- **节点各自 clone / 维护实例检出**：拒。违反「主节点是唯一内容源」，实例改动要逐台同步。
- **运行时按节点缓存物料**：暂拒。当前体量几十 KB，按作业复制简单且无版本歧义；技能源明显变大再评估。
- **共享 / 隔离检出标记**：拒。写入形态是这次派活的意图，不是目录的持久属性；标记会把「这次允许」变成长期默认。
- **盘点共享目录的并发写（锁）**：拒。你明确要的是「用户主导、用户决定何时合并」；锁只增加状态与失败模式，脏门禁 + 不 commit 已经足够。
- **派活时在节点自动 clone 缺失的检出**：拒。用户要的是「机器上已有的目录」；自动 clone 会把「这台机器还没准备好」变成难以察觉的隐式网络动作与磁盘写入。缺检出就 fail closed，由人补 `checkouts.yaml` 或先 clone。
- **写作业前自动 `git init`**：拒。把用户目录变成仓库是用户决定的事；这里只拒绝并提示。
- **项目进主题闭集**：拒。主题是「派给谁」的调度键，项目是「在哪干」的执行键；混成一个会让主题闭集长出第二套分类（ADR 0012 的教训）。

**Consequences：**

- 三台节点在补 `checkouts.yaml` 之前无法承接项目作业——这是有意的显式缺口，不会被自动 clone 掩盖。
- `targets` 里可以有「没有该项目检出」的节点：它只是不能接**项目**作业（派活 fail closed），不带 `--project` 的作业（在机器上调研、跑运维命令）照旧可派。石秀那类只读调研员就是这样用的——location 本身是任务语义。
- `direct/` 脚本不再能靠自身位置找仓库根，`worktree` 改为按项目/检出参数解析；`server` 在节点物料里必然失败（预期）。
- 原地写的保护是过程性的（脏门禁、禁用 git 写、结果文件附 `git status`），不是结构性隔离；用户接受这一点，换取「在自己目录里直接看效果」。
- 推翻两条既有结论：ADR 0025「技能真源不复制」在本机继续成立、节点侧改为按作业复制；ADR 0041 / 0042 的 `instance_root` 与「节点同布局」前提退场，寻址制、outbox、fail closed 不受影响。
- 上线顺序：三个新声明文件可以先落地（旧二进制不读），`instance_root` 删除与新二进制必须同批，否则旧节点声明会让新二进制直接报错。
- 写形态不校验能力是否只读：`--in-place` / `--worktree` 只按「能力声明的项目 + 检出状态」判，不读手册里的读写边界。只读能力（石秀）仍靠手册自律——与改动前一致；要硬约束得另加一个能力字段，本 ADR 不做。
