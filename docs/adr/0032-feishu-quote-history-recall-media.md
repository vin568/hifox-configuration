# ADR 0032：飞书通道补齐引用上下文、历史查询、撤回与图片回帖

飞书是主控对用户的唯一通道，但到 2026-11-20 仍只支持「收一条文本 / 发一条文本」。四项缺口
逐个对应一个用户被迫补位的场景：

- **回复**着消息说「这个再改一下」「图里这里错了」时，事件里的 `parent_id` / `root_id` 没人读，
  被回复的正文与图片都不进注入——主控只看到一句无指代的话，要么猜错对象返工，要么回问
  「你说的是哪个」。
- 用户说「昨天说的那个 bug」而主控刚换过脑（ADR 0022/0030）时，没有任何自助手段，只能让用户
  重发；换脑越频繁，断层越常见。
- 主控回错人、说错结论、把内部术语发进用户群时，只能请用户手动撤回——把纠错责任外包给用户。
- 验收结论要配截图时，`reply` 只能发文字，证据留在本机 `media/`，用户得自己去翻。

四个缺口共用两条新接口（读单条消息、删消息）与一次投递链改造，一次做完。

**决策：**

- **引用上下文按需只取一层**。事件带 `parent_id` 时取父消息、只有 `root_id` 时取根消息、
  与自身相同视为无引用（防脏数据自指）。取到的消息走**同一个** `extractMessage` 提取正文、
  走**同一个** `mediaStore.Save` 落盘附件——资源接口的 `:message_id` 是资源所属消息，必须传
  被引用消息 id（传当前 id 会 404），路径 `media/<父id>/` 本身就是出处证据。被引用消息自己也
  是回复时不再展开：一次回复不该扇出整条链的请求与延迟。**任何失败都不阻断本条注入**，
  而以带原因的降级块出现（已撤回 / `code=… msg=… request_id=…` / 超时），主控必须知道
  「这条是回复」，否则又会当成上下文完整。无引用的普通消息零额外 API，注入文本逐字节不变。
- **引用块渲染在 `<current_message>` 之前**，`message_id` 恒输出、`from` 有值才输出；
  `Quote` 为 nil 时一个字节都不加（黄金用例钉死）。引用正文按 rune 截断到 2000，附件最多落 4 个，
  超出只留 key 占位，防一次回复扇出十几次下载。
- **历史查询是只读命令，产物是纯文本**。`superctl history --chat <id> [--limit] [--since]` 与
  `--message <om_...> [--download]`，输出时间/发送者/正文的单行摘要（多行折叠、200 rune 截断），
  不把 API JSON 抛给主控，不注入、不写状态、不进 outbox。列表只取一页（`page_size=limit`，
  不翻 page_token）、不下载附件（要文件用 `--message <id> --download`）；`--limit` 1..50 是平台
  上限，`--since` ≤168h 是**产品收敛**（平台没有 7 天窗口限制），参数越界当场报错、不发网络请求。
  不做姓名解析：要 `contact` scope 且多一次调用，显示 id 足够主控定位。
- **撤回的前提是发送时记住 message_id**。`send` 回填 `resp.Data.MessageId`；缺 id 时**不判失败**
  ——消息已经出去了，让 `Drain` 重试会让用户收到重复消息；宁可丢撤回能力（撤回时给出「旧版本投递」
  提示）。outbox 的 `Entry` 因此多 `message_id` / `recalled_at`，「哪条能撤」收敛成一个谓词
  `sent_at != nil && message_id != "" && recalled_at == nil`。`recall --id/--message/--last` 三选一，
  `230110`（消息已不存在）按**成功**处理并把本地记为已撤回：目标状态（消息不可见）已达成，
  重试必须收敛。重复撤回只输出 `already_recalled`，不发请求。
- **撤回时限不在本地预判**。飞书不提供「还能撤多久」的查询，时限由企业管理员在管理后台设置，
  `230009` 是唯一权威。本地时钟不是服务端真值，提前拒绝会误伤把时限调长的企业。
- **图片回帖恒为一条消息**：`reply --image`（1..9 张）上传后按「纯图 1 张 → `image`；
  文字+图或多图 → `post`」发送，纯文字仍走 `msg_type=text` 原 payload（逐字节不变）。
  一个 message_id 保证撤回粒度与消息一致。上传放在**投递时**而不是 `reply` 时：`reply` 必须
  保持纯本地、断网可用（它是主控回话的唯一通道），代价是重试会重传（单图 ≤10MB、最多 8 次，
  可接受），换掉的是「outbox 里存 image_key 可能过期」这种失败模式。**全有或全无**：任一上传失败
  一条都不发，不产生半条消息。文件不存在、是目录、0 字节、>10MB、格式不在白名单，都在 `reply`
  阶段报错，不排队等 8 次重试。
- **投递在数据锁之外进行**。`Drain` 原先整段持锁（含一次 send），图片上传把单次投递从一次
  Create 扩成最多 9 次上传 + 1 次发送，60s 预算全落在锁里会挡住 `Append`（`blockedNotifier`
  与指令回执都走它）。改为「快照 → 无锁逐条投递 → 回锁按 ID 合并结果」，`drainMu` 保证同一时刻
  只有一个 Drain。`Sender` 另设 `timeout`（60s）包住单条投递：`Drain` 串行，一个卡住的上传
  不能阻塞主控所有回帖。

**Considered Options：**

- **引用块失败时干脆不输出**：拒。主控会把「回复」当成新需求，答非所问比缺一块更贵；降级块
  至少说明「这条是回复、内容取不到」。
- **展开整条回复链**：拒。一次回复扇出 N 次 API 与下载，延迟与配额都不受控；一层足够回答
  「他在说什么」。
- **把历史 JSON 直接给主控**：拒。主控要的是「上面聊了什么」，不是再学一遍平台字段；渲染成本
  低于每次解释成本。
- **`history` 自动翻页拉满窗口**：拒。一次查询的耗时与配额要可预期，更长历史由用户收窄窗口或
  加大 limit。
- **本地预判 24h 撤回窗口**：拒。时限由企业配置，本地时钟不是真值；只按 `230009` 报。
- **缺 message_id 时判发送失败**：拒。消息已发出，重试等于重复打扰用户；宁可丢撤回能力。
- **`reply` 时上传并缓存 image_key**：拒。`reply` 会因此依赖网络，断网时主控连「收到」都发不出去；
  且 image_key 有过期风险。
- **文字一条 + 图片一条**：拒。破坏「一次回帖一个 message_id」的撤回语义，用户也会收到两条推送。
- **`Drain` 继续整段持锁**：拒。见上：上传把锁内时延放大一个数量级。

**Consequences：**

- `internal/feishu` 新增 `apierr.go` / `query.go` / `quote.go` / `history.go` / `post.go`，
  `serve.go` 多 `quote` 依赖与 `parent_id`/`root_id` 解析，`probe.go` 事件行多 `parent_id`；
  `internal/inject` 的 `Payload` 多 `Quote`；`internal/outbox` 的 `Entry` 多两个字段、`Drain` 回调
  改成 `func(ctx, Entry) (string, error)`、新增 `Get` / `LastRecallable` / `MarkRecalled` /
  `MarkRecalledByMessageID`；`cmd/superctl` 新增 `history` / `recall` 两个命令、`reply` 多 `--image`。
- 本轮唯一可能新增的飞书 scope 是**群聊历史**的 `im:message.group_msg`（需在开发者后台申请并
  发布版本，属部署动作）；其余权限（`im:message` / `im:resource`）已在用。缺 scope 时命令以
  `230027` 失败并点名该 scope。
- 出站图片不落 media：outbox 只存绝对路径，原文件在投递前被清则按 8 次预算死信（`last_error`
  里有路径）。不在出站方向复制用户文件是有意的。
- `post` 里的图片比 `image` 气泡小；若用户反馈太小，备选是拆两条消息，但那会破坏撤回语义。
