# 吴用意图判定：默认咨询，显式动作或具体确认才交付

用户在飞书里的一句话通常同时包含「现象 + 期望」，例如「登录页 500 了」「这个 bug 修一下」「排查下发布门禁为啥失败」。吴用必须决定：派堂 / 舵做排查答复（咨询），还是建任务交给专家做完整交付。两类误判的代价不对称：把咨询误判成交付会污染任务板、派错人、浪费专家时间（与 ADR 0002「聊天链路零任务增量」直接冲突）；把交付误判成咨询只是多一轮确认，且排查结论能让任务正文更准确。旧规则「仅用户显式要求或排查后确认」只有原则、没有可操作定义，模型在「修一下」「看着办」这类表达上会漂移。

**默认咨询。** 判定按有序规则表执行（指令正文 `instructions.md` §1.1），命中即停：

| # | 信号 | 判定 |
|---|---|---|
| 1 | 明确「先别建任务 / 只要排查」 | 咨询 |
| 2 | 明确动作指令 + 主题 + 期望结果 | 交付 |
| 3 | 疑问 / 诊断动词（为什么、看看、排查、定位、分析、怎么改） | 咨询 |
| 4 | 只陈述现象 / 报障（无请求动词） | 咨询（结论末尾提议建任务） |
| 5 | 对**具体提议**（主题 + 范围 / 验收；承接人由吴用内部决定、不对外）的同意 | 交付 |
| 6 | 其它 / 置信度低 | 咨询 + 一次澄清 |

配套定义：

- **明确动作指令** = 祈使句 + 会改变代码 / 配置的动词（修复、改掉、加上、实现、优化、升级、发版、建任务、排期、指派），对象落在主题闭集内；「这个要改」只是判断，不是指令。
- **确认**必须针对具体提议；泛泛的「嗯 / 行」不算。
- **建任务自检**：主题在闭集、标题可写、需求原话 + 结论、验收要点、同层级承接人；缺一两项先补问，缺两项以上先排查或让用户补。
- **最多问一个**能改变动作的澄清问题；仍不清则先排查。
- **意图入账**：台账事项记 `意图：咨询 | 交付`；咨询转交付时新建交付事项并以 `关联项` 指向原咨询，不把已收口的咨询改写成任务。
- **后台巡检不建任务**：`wuyong-ledger-sweep` 只做状态真值对账，永不触发交付。

## Considered Options

- **开场先问「要排查还是建任务？」**：拒。多数消息是咨询，先问增加摩擦；且没有排查结论时，用户也说不清任务范围。
- **见到祈使句就建任务**：拒。会把「帮我看看怎么改」这类咨询变成任务卡，违反 ADR 0002 的零任务增量。
- **让模型自报置信度、低置信度再问**：拒。置信度不可审计、不可回归测试；有序规则表可以逐条核对。
- **一律咨询、永不建任务**：拒。忽略用户明确的交付指令，完整交付失去入口。
- **独立 LLM 分类器 / 路由模型**：拒。闭集只有两类，规则表已覆盖；引入分类器增加不可解释性，且模型判定仍要落到同一张表。

## Consequences

- 模糊的「修一下吧」可能多一轮确认——这是刻意选择的安全侧偏置。
- 线上故障类描述默认先诊断（快、可逆），诊断结论再决定是否建任务；不会自动建紧急任务。
- 用户明确说「建任务」但缺验收要点时，只补问缺失项，不创建含糊任务。
- 意图写入台账，历史可按事项追溯「当时是咨询还是交付」；咨询与交付通过 `关联项` 成链。
- 规则表是指令正文的一部分；改动必须同步本 ADR 与 `GLOSSARY.md` 的「意图判定 / 完整交付」，避免多处表述漂移。
