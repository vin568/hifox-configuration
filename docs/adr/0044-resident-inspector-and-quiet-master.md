# 巡检改由常驻巡检者执行，主控只在有发现时被叫醒

主控的上下文是运行时里最贵的资源（ADR 0022 的实测：单会话已到 1.9 MB / 441 条消息），但巡检的注入是**无条件周期性**的：`superctl serve` 每 `tick_interval`（当前 10m）跑一轮 `sweepOnce`，三源判据几乎永远为真（实测活跃台账 31 个文件、在途 10 条），主控每天被叫醒约 144 次，每次都要在自己那一轮里重新逐条对账。另有 `scanContextAlerts` / `scanLocalHealth` 两条机器扫描绕过三源判据直接注入主控，把「确定性判据」和「需要判断的对账」混在同一条通道里，且没有任何去重之外的结构阻止主控被机器噪声撑满。

同时存在一个结构性缺口：**在途作业的真实状态只有主控在对话回合里才被核对**。用户不发消息，作业就没人对账——巡检的价值就在这里，所以不能简单把周期拉长。

**决策：**

- **新增常驻巡检者 `role: inspector`**（实例：时迁 `shiqian`，`workspace: crew`，常驻）。框架的角色闭集从 `master | retro | job` 扩为 `master | retro | inspector | job`；`role: inspector` 与 `retro` 同一套常驻语义（boot 起它、`fresh` 换脑名单包含它、`dispatch --local` 注入既有 pane 而不是新起、`cancel` 不关 pane），至多一个，缺省允许 0（未声明时巡检回落为运行时的机器判据 + 主控直注，行为等同今天）。
- **巡检者只做本地面**：在途清单 ↔ herdr agent ↔ 结果文件 ↔ 活跃台账四方对账，产出「需要处理」的发现。**平台侧真值仍归哨兵**（ADR 0009）：巡检者不调 `hifox`、不读平台任务状态，两条通道各管一层，避免同一终态出现两个上报源。
- **发现是一条结构化记录，不是一次 `report`**：发现写 `state/findings/<id>.json`，字段为类别、对象（作业/事项）、摘要、发现时间、状态（未投递 / 已投递）。运行时只在**存在未投递发现**时向主控注入一条 `[触发器: sweep]`，投递成功后标记已投递；主控 blocked、急停、巡检者崩溃时发现留在文件里，下一轮重试。于是「非空才叫醒」是机器真值，不依赖模型自觉。**条件消失即删除（消解），不留「已消解」态**：发现是条件的镜像，不是事件史；同一对象同一时刻只能有一个当前条件（上下文级别升级/回落、健康条件从 stalled 变 lost、条目离场都要先删旧再写新，否则主控会对着过期事实处置）。
- **机器判据保留、只换出口**：`scanContextAlerts`（上下文临界）与 `scanLocalHealth`（僵尸在途、结果就绪、停滞）判定逻辑一行不改，输出从「直注主控」改为「写一条发现」，与巡检者的发现共用同一投递通道与去重身份。**不把确定性判据降级成 LLM 判断。**
- **巡检者与蒋敬同用 `crew` workspace，但必须各占一个 pane**：herdr 的根 pane 只能承载一个 agent，第二个常驻 agent 要在同一 workspace 里分新 pane（`pane split`）。首次上线时实测 `agent_pane_busy`——这是「多常驻」的必要条件，不是环境问题。
- **巡检者的权限档**：只读检测 + 只追加台账的 `最近核对` / 异常标注（单写者例外，与吴用巡检同构）。不重试、不 `tell`、不重启服务、不派活、不对外发消息——这些动作仍归主控，由发现触发。发现用 `superctl finding add|resolve|list` 写，不手写 JSON：类别闭集与事实身份由命令面校验，投递侧不会出现「永远投不出去的坏文件」。
- **派发门禁**：三源判据（活跃台账 / 在途清单 / 活动 agent）全空时不派发巡检者，零成本；上一轮还在 `working` 时本轮为 `busy-skip`（不是失败，不计入失明告警）；单轮超过 2 个 tick 未结束视为卡住，按健康通道上报。
- **巡检轮次不建台账条目**：每 10 分钟一轮的例行对账不是「一件工作」，写进活跃区会把台账撑爆（当前已 31 个文件）。派发层对 `role: inspector` 跳过台账骨架；日度复盘仍一作业一文件。
- **哨兵的两处缺陷同批修**：① `refreshTarget` 失败不得中断轮询——注入失败才不推进快照，轮询本身照跑（实测 `serve.log` 里 `platformwatch ensure failed` 累计 1076 次，主控不在时哨兵跟着失明）；② 新增**覆盖差集**检查：本实例声明的平台 agent 承接的活跃任务 × `inflight.json` 的差集，报「平台在跑但从未登记」的事件（HF-16239 类）。判据必须收窄到「本实例声明的承接者」：只看 `delegate.type=agent` 会把全组织的任务都算成漏登记（HF 空间实测 42 条，绝大多数与我们无关）；收窄后同一空间只剩 2 条真漏登。差集提示用户确认后补登：`superctl track --platform hifox --task <任务号>`（上游已合入）；补登后哨兵才开始跟踪，判定不归我们的就不动。

**Considered Options：**

- **把 `tick_interval` 拉长（如 30m）**：拒。省的是唤醒次数，不是每次唤醒的成本；且把「作业无人对账」的窗口一并拉长。
- **复用蒋敬（`role: retro`）兼职巡检**：拒。`retro` 至多一个且已承担日度复盘，节奏（10m vs 每日）与产物边界都不同；ADR 0013 / 0015 已因同类理由否决过把不同任务并进一个 automation。
- **每轮动态拉起 `role: job` 巡检**：拒。144 个 pane / 天、每轮重新 prime，且 `done` 事件仍会叫醒主控——等于没改。
- **让巡检者直接 `superctl report` 而不落发现文件**：拒。`report` 在主控 blocked 时直接失败，内容只落结果文件，没有重试结构；发现文件把「是否已送达」变成可观测状态，并且天然就是去重面与审视的审计面。
- **巡检者也查平台任务状态**：拒。与哨兵重复（每分钟一次的确定性判据），并让同一终态有两个上报源——Q19 刚收掉的重复问题会在平台侧重演；且巡检者不需要 `hifox` 登录态，权限面更小。
- **删掉机器扫描、并入巡检者的检查清单**：拒。把确定性判据换成模型判断，漏报面变大；保留计算、只换出口的代价几乎为零。
- **让巡检者拥有重试 / 重启 / `tell` 权限**：拒。这会让它成为第二个执行者，破坏「主控是唯一处置者」的单点；检测与处置分离，处置必须经主控与用户。

**Consequences：**

- 主控的周期性唤醒从「每 10 分钟无条件」变成「有发现才发生」；巡检者自身约 144 轮/天，但每轮只读文件与 `herdr agent list`，不调平台 API。
- 出现新的单点：巡检者失明（进程死、卡住、注入失败）时没人发现异常。由运行时兜底——巡检者连续 3 个 tick 没有成功轮次即注入主控告警，`superctl status` 暴露巡检者健康（最近成功轮次、连续失败、busy-skip 计数），3h 审视与蒋敬复盘都读它。**兜底报警由机器真值发出，不允许巡检者自报自己失明。**
- `role: inspector` 是框架改动，涉及能力注册表校验（至多一个）、`boot.Ensure` 起停、`internal/boot.Fresh` 换脑名单、`dispatch --local` 的常驻分支、`done` 事件豁免（巡检者回合结束不叫醒主控）；需要一条框架 ADR 与框架 GLOSSARY 的角色词。
- 巡检者不做平台状态核对后，平台侧的漏报面完全由哨兵承担——因此哨兵的可用性（缺陷①②）从「体验问题」升级为「正确性前提」。
- 「最近核对」的写入者从「主控每轮」变成「巡检者每轮 + 主控收口时」，单写者语义需要按 ADR 0005 的例外条款显式扩写。

**依据：** 本仓 ADR 0005（台账形态与巡检写权限）、0022（注入卫生）、0029（回报通道）、0030（上下文测量）；框架 ADR 0007（角色契约）、0009（平台停滞与拒执）、0022 等价机制见 `vendor/super-agent`。实测数据取自 2026-11-25 的 `~/.local/state/songjiang/`：活跃台账 31 文件、在途 10 条、`tick_interval=10m`。
