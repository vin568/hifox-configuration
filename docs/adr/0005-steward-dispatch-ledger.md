# 吴用跨会话工作记忆：文件夹式调度台账（一事项一文档）

吴用（`agents/wuyong`）的会话上下文靠执行机上的运行时会话续接：服务端存 `conversation_messages`，普通轮次不回放，`/new` 清 resume 指针而非删消息（`server/pkg/db/queries/chat.sql:327-341`、`server/internal/handler/daemon.go:5797-5840`）。运行工作目录默认 7 天 GC，平台不存在按 agent 隔离的持久目录，也没有内建 agent 记忆。因此「已经做过什么 / 正在跟进什么 / 将要做什么」必须落到平台内一个持久、可写、可跨会话读的载体。

本决策把载体定为 **Space 共享文档的文件夹式台账**：HiFox 产研 Space 的 `Agents` 文档集下，每个部署实例一个文件夹（`吴用` / `吴用 (staging)`），内含 `计划` / `等待用户` / `进行中` / `已收口/<YYYY-MM>` 四个文件夹；**一个事项一份文档**，状态由所在文件夹表达，索引由文件夹列表提供。读写协议收在 agent skill `wuyong/ledger`，instructions 只留「何时读、何时写、失败怎么降级」。

## 生命周期划分（终态不等于成功）

文件夹是生命周期状态的完备划分，每个事项任一时刻恰好属于一个：

| 状态 | 文件夹 | 判定 |
|---|---|---|
| 计划中未启动 | `计划` | 有触发条件 / 时间，无平台对象在跑 |
| 等待用户决定 | `等待用户` | 是否建任务、是否重试、是否继续 |
| 活跃或等待非用户主体 | `进行中` | 未收口：平台对象非终态，或终态已发现但尚未转述（`状态：待转述（verdict）`）；workflow running、任务未关闭、等待专家 / 外部依赖（正文标 `状态：阻塞`） |
| 终态（成功 / 失败 / 取消 / 重复） | `已收口/<YYYY-MM>` | 已转述且不再有后续动作；verdict ∈ `成功 / 失败 / 取消 / 重复` |

- **收口 = 转述之后**：后台巡检查到终态时只标 `待转述（verdict）`，**不改名、不移动、不归档**；下一次用户对话先转述，再按 verdict 归档（失败 / 取消在转述后先移入 `等待用户`，用户放弃才归档）。

- 终态文件夹命名为 `已收口` 而非「已完成」：失败、取消、重复不是「完成」，但都是终态；verdict 写在文件名后缀与时间线末行，列表即可分辨。
- **失败但可能重试不是终态**：放 `等待用户`（问是否重试）或留在 `进行中`（已决定重试并追加新 execution）；提前归档会让下一次重试变成「新事项」，破坏一件事项的连续性。
- 同轮办完的杂活不建文档；只承接有后续义务的事（等待、跟进、计划）。
- 不按会话拆文件：一个会话可产生多个事项，同一事项可被后续会话读取 / 接管。

## 本体不轮询：状态真值与异常处置

吴用本体只在用户发消息时运行；无对话期间的状态修正由已启用的后台巡检承担（见下），但任何回答仍以本轮查询为准。文件夹里的状态是「最后一次核对的结果」，不是实时状态：

- **写入 `进行中` 的充分必要条件**：本轮查询成功，且平台对象存在——非终态，或终态已标 `状态：待转述（verdict）` 且尚未转述。否则只能写 `等待用户`（待决策）或 `已收口`（已转述的终态）。
- 每条事项记 `最近核对`；回答进展前必须本轮重查，超过 24h 未核对的先核对；没有本轮查询证据，不允许写「执行中」。
- **派发成功但拿不到 execution id**（命令超时 / 输出不可解析）：不得写成进行中；用 `workflow logs list --workflow <id> --space "<Space>" --filter '{"startDate":"<10 分钟前>"}'` 找回，找不到转 `等待用户`（重派 / 取消）。
- **异常闭集**：派发结果未知、幻影项（有 id 但平台不存在）、瞬时失败（启动即失败）、卡住（`pending` > 10 分钟或 `running` > 120 分钟）、暂停待输入、任务无执行者（无 delegate 且无人类 assignee，或 delegate 已归档）。正常终态不属异常：成功 / 取消（workflow `cancelled`、任务取消或拒绝）/ 任务关闭都按 verdict 处理。发现异常即报；**自动修复仅限状态真值**：终态 → 标 `待转述`（前台转述后收口），幻影 / 未知 → `等待用户` 并写明原因；重派 / 取消 / 转任务一律等用户决定。
- **后台巡检的写权限**：只追加终态结论行，更新 `状态` / `最近核对` / 时间线；终态一律只标 `待转述（verdict）`，不改名、不移动、不归档——巡检无法把结果送到用户面前，收口必须由前台对话完成。
- **本体不做后台轮询**：不声称「监控中 / 持续跟踪」，只报「最近核对：<时间>」。对话之外的检测由已启用的 automation `wuyong-ledger-sweep` 承担（见 Consequences 的「后台巡检」条目）。

## 并发：为什么不是一份共享总台账

- 平台事实：`docs document edit` 是整文替换、**无版本锁**，服务端按次留版本快照但 CLI 读不到；没有 CAS / If-Match / 文档锁。`docs search` 只搜文档名。
- 平台事实：会话内 run 是**排队串行**的——同一会话可以有多个待运行 run，但只有队首可被 claim（`server/pkg/db/queries/chat.sql:828-930` 的队首谓词、`ListChatQueueHeadRuns`、`IsQueuedChatFollowUp`）。`agent_runs` 上那个 `idx_one_pending_run_per_task_agent` 覆盖 `(task_id, agent_id, conversation_id)`，而 chat run 的 `task_id` 为空（NULL 在唯一索引里互不相等）——**它不是会话串行的保证**，不要拿它当依据。
- 结论：同一会话不会并发写；并发只发生在不同会话之间。按「事项」划分**语义单一写者**即可无锁——事项由创建它的会话独占修改请求、结论与状态，其他会话只读；跨会话可见性由文件夹列表提供（每份文档的创建/移动在服务端是原子操作）。共享可变文档只会把并发写成静默丢更新，直接排除。廉价保险：写前重读 `最近核对` 与时间线末行，被改动过就合并再写。
- **唯一授权的第二写者**：后台巡检只追加终态结论行、状态与 `最近核对`，不改请求与既有结论，且跳过 5 分钟内前台刚更新的事项；其余并发冲突仍是单条后写者覆盖 + 版本快照兜底。

## 容量：为什么每轮只读未完结事项

市面 agent 记忆机制的结构是一致的：OpenClaw 的 curated core（常驻、受 bootstrap 预算截断）+ episodic 日记（不进 bootstrap，靠检索）+ dreaming 整合；Hermes 的硬字符上限（写超即报错，逼同轮整合）+ 会话开始时的冻结快照 + `session_search` 明细检索。即「**常驻层有上限、明细层按需检索、整合把明细移出常驻层**」。

本台账同构：常驻层 = 未完结事项（只随真实在办工作增长），明细层 = 事项正文，历史 = 按自然月归档后按名检索，平台真值（执行/任务状态）永不复制、用关联键现查。

## Considered Options

- **单一总台账文档 + 先读后写**：拒。无 CAS/版本锁，两次 HTTP 之间就是丢失更新的窗口；OpenClaw 的哈希校验依赖本地原子 rename，平台给不了。
- **常驻任务 + 评论追加作日志**：拒。评论可编辑、可硬删（无墓碑），单次读取上限 2000 行，且把调度噪音带上任务板，与 ADR 0002「聊天链路零任务增量」冲突。
- **每会话一份文档**：拒。写冲突没了，但跨会话不可见——恰恰丢掉「知道别的会话在跟进什么」。
- **任务 `metadata` / 自定义字段**：拒。`metadata` 8 KB 硬上限，自定义字段每（任务，字段）单值，放不下增长型状态。
- **本机文件**（`~/.hifox/lessons/<key>.md` 之类）：拒。运行目录 7 天 GC、无 per-agent 目录、同用户所有 agent 共享 `$HOME`，换机即丢且不可审计。
- **workflow `memory` 块**：拒。属随包 vendored 的 Sim 引擎，CLI 面不可达，agent 执行对 `/rest/v1/wf/**` 被服务端拒绝。
- **等平台内建 agent 记忆**：拒。现网无此能力，权限与形态不可控。

## Consequences

- **没有人类一眼可读的总快照**：可读性由目录结构承担；需要汇总时临时列文件夹生成，不落盘、不作为权威。
- **文档数随已收口事项增长**：按自然月归档，永不自动加载；不自动删除，仅用户明确要求才 prune（删除前列清单确认）；超过 12 个月的归档在容量提醒中提示可 prune，默认保留。
- **检索能力受限于文档名**：事项名必须含主题 + 标题关键词；收口时追加 verdict 后缀，正文结论行同 verdict，保证「成功 / 失败 / 取消 / 重复」可按名筛选；正文不参与搜索。
- **极端并发下的可接受损失**：两个会话同时收口同一事项时后写者覆盖，影响仅限单条，服务端版本快照可回溯；文件夹同名竞态用「先 list 后 create、用第一个、不删除」兜底。
- **接管语义**：仅当事项已终态且 10 分钟未更新时，新会话可接管一次（先重读再追加/移动），不复制、不重建；仍非终态时只读汇报。
- **异常暴露窗口**：没有常驻进程；后台巡检（每 30 分钟）健康时把「进行中但无执行者」的窗口压到 ≤30 分钟，巡检失败或延迟时退化为下一次用户交互；用 `最近核对` 时间与回复开头的异常汇报收敛预期，不声称实时监控。
- **后台巡检（已启用）**：automation `wuyong-ledger-sweep` 每 30 分钟（`*/30 * * * *`，Asia/Shanghai）按同一套真值规则对账「进行中」事项：终态 → 标 `待转述（verdict）`（不归档）；幻影 / 派发结果未知 / 卡住 / 暂停待输入 / 任务无执行者 → 按异常表标注。只在有变更或异常时向 CLI 用户发一条私聊摘要，无变更零打扰。不重派、不取消、不归档、不碰「等待用户」「计划」，跳过 5 分钟内刚被前台处理的事项。巡检失败或延迟不阻塞，下一次巡检或用户回合再收敛。
- **巡检通知走 HiFox 私聊**：automation 没有飞书出站面，异常提醒以 HiFox DM 为准；飞书侧仍以下一次对话的当场核对为准。两个环境各一份实例（prod / staging），分别对账各自台账。
- **文档不在声明式面内**：x-deploy 只部署 skill、instructions 与巡检 automation；台账文件夹与事项由吴用首次使用时自举，id 不硬编码。
- **失败必须可见**：台账不可读 / 不可写时，吴用在本轮回复中显式标注「记忆不可用」，绝不假装记得；`/new` 后先列文件夹恢复在办事项，而不是要求用户重述。
