# ADR 0024：任务正文由派活员写、附件在注入边界落盘

2026-11-18 的一次真实派活（HF-16095）照出两个独立缺陷，两个都发生了：

- **用户在飞书里贴的图消失了**。消息是富文本（`msg_type=post`），文字段落末尾带一个 `img` 元素。提取层按 `tag` 只认 `text`/`a`/`at`，`img` 落到不存在的分支被静默跳过——注入文本里既没有图片、也没有 `image_key`，主控手上连「这里有张图」的线索都没有。纯图片消息（`msg_type=image`）同样只降级成 `[媒体消息]`，不带 key。
- **平台任务的 description 是派活信封的原文**：「需求原话：…；层级：staging；验收要点：…；来源：主控转交」。信封是主控写给派活员朱贵读的**路由输入**，被 `--body` 原样透传成了给承接人看的任务正文；没有任何一处负责产出人话正文。

两条的共性：**注入边界上的信息在往下游传时被当成同一种东西**（图片 = 文字、信封 = 任务正文），而真正的载体（文件、正文）没有在接口上出现。所以本 ADR 不给「下游补格式」的方案，而是把两种载体的传递改成显式的。

**决策：**

- **附件在注入边界落盘，注入文本里只出现本地路径**。飞书消息里的 `img` / `file` / `media` / `audio` 在 `internal/feishu` 提取时保留 key 占位（`[图片 <image_key>]` / `[文件 <name> <file_key>]`），`serve` 收消息时按 `im/v1/messages/:id/resources/:key` 下载到 `state_dir/media/<message_id>/`，并把占位原地改写成路径（`[图片 /…/img_v3_….jpg]`）。**不把二进制塞进注入**：主控是纯文本会话，图片进不去也不该进；路径进得去、能留证、能转派。
- **下载失败不丢消息**：占位退回带 key 的形态（下载不了也还能人工补），只记一条 warn。附件缺失从来不是丢掉整条用户消息的理由。
- **平台任务的正文由派活员写、经 `--desc-file` 落成 description**。主控只转发用户原话与附件（`dispatch --local`），**不产出文档**——主控是最该保持响应速度的角色，让他先写一篇 markdown 是把用户晾在门口。朱贵收到原始材料后用 heredoc 写一份**写死的 `/tmp` 路径**的正文（背景/现象/复现/期望/环境/验收/来源；不用 `mktemp`/shell 变量——每次 bash 可能是新 shell，变量不跨命令），`superctl dispatch --platform hifox --desc-file` 把它映射成 `hifox task create --body-file`（markdown 原文，不过 `\n` 转义、不经任何重组）。
- **`--desc-file` 只属于平台通道**：本地派活带它当场报错。正文的撰写权在派活员，工具面上不提供第二条路——否则「主控顺手写一下」会悄悄回潮。
- **正文归档**：建单后运行时把最终正文（含运行时补的嵌图小节）存成 `state_dir/briefs/<任务号>.md`，路径回报在结果的 `brief` 字段；主控复查「这单写了什么」读它，不必开网页，也不怕临时文件被清。
- **平台派活不再接受 `--body`**：信封只走本地通道（主控 → 派活员），到了建单那一跳必须给正文文件，否则当场报错。**改语义要红，不要静默**——把 `--body` 保留成「照样进平台」的老行为，等于把 HF-16095 的形状留在工具里。
- **派活员写正文、主控不写**：这是修订后推翻初稿的一处。初稿让主控写正文（理由是「内容不在朱贵手上」），运行后确认代价在另一边——主控是用户的唯一入口，任何「先写一篇文档」的前置都会拖慢受理；而朱贵手上确实有全部原始材料（主控转发的用户原话 + 落盘附件路径），整理成任务描述是机械工作，正是 job agent 该干的。**分工据此定为**：主控只判「类型」并原样转发材料，朱贵判「转给谁 + 写成什么样」（挑人与一篇文档）。派活员仍不许脑补：用户没给的信息写「待补充」，缺的是能改变动作的信息才回「需要澄清」。
- **建单后补的步骤都落在同一张单上**：图片附件用**任务自身**的 `attachments[].preview.url` 按上传顺序嵌进正文（`## 截图（按上传顺序）` 小节，`task edit --body-file` 回写，并把正文文件同步回写）；文件与视频不嵌——平台不给它们的 preview（`preview.type=none`），嵌空图只会坏版。**不重建任务**：附件数对不上、嵌图失败都回报成 `build_notes` 让人在原单上补；重试建单就是 HF-15793 的双会话事故换了个形状。
- **任务号输入走 `--update`，不新建**：用户拿着任务号来「补充一下」时，`dispatch --platform hifox --update <任务号>` 走 `task edit`（正文替换、附件追加、类型/优先级/迭代可改），并**拒绝** `--agent/--instance/--space/--title`——改派或换 Space 会让承接人再开一次执行，改标题会让用户认不出原单，「补描述」不该有这些副作用。任务号全局可解析，这条路径不钉组织。
- **任务类型由人判定、显式传 `--type`**：平台有默认类型，默认值标错没人会替你发现——HF-16095 标题写了 `[bug]`、类型是「需求」。类型是语义判断，所以只在主控那一侧定（信封写「类型：Bug|需求|未指定」），派活员照传、不猜；拿不准就留空用平台默认并在正文里说明判断标准。
- **附件三跳都显式**：`--attachment` 从主控 → 派活员 → `hifox task create` 一路是同一个参数、同一份路径（可重复）。派活员手册里写死「注入里列出的每个附件路径都要带上」，本地派活的 prompt 也单列 `[附件]` 段——混在正文里靠自觉一定会漏。
- **落盘附件的卫生**：目录 `0700`、文件 `0600`、不进 git；默认保留 30 天（`media_retention` 可调），下载时顺手清理（同一进程内最多每天扫一次，`sweepMu` 保护——飞书 SDK 每条消息一个 goroutine，`Save` 会被并发调用）。用户原图不是长期资产，够复现、够转派即可。

**Considered Options：**

- **在 `dispatchHifox` 里剥前缀重组正文**（原报告 A2）：拒。格式仍机械（拼出来的仍是信封字段），而且语义是猜的；同样的重组逻辑迟早要在别的平台复制一遍。
- **让主控写正文**（初稿方案，后被推翻）：拒。主控是用户唯一入口，先写一篇 markdown 会把受理拖到几十秒以上；而原始材料随信封一次性转给派活员，他写正文时并不缺料。见决策里的「派活员写正文、主控不写」。
- **让朱贵按模板机械抄信封**：拒。抄出来的是「有格式的信封」而不是任务——所以 §0.5 要求他整理（现象/复现/期望/验收），并允许对缺料回「需要澄清」。
- **把图片二进制塞进注入**：拒。主控是纯文本会话，图片进不去；即使进得去，注入文本的体积与上下文卫生（ADR 0022）也受不了。
- **让主控读图片内容再描述**：拒。当前无多模态入口，且描述会失真；路径 + 平台附件上传本身就是无损通道。
- **正文作为 `--desc` 内联参数传**：拒。markdown 经两层 LLM 驱动的 shell 传递，转义与换行必然出错；文件路径只有一个，且可复查。
- **不落盘、注入里只带 `image_key`**：拒。key 只有配 token 的人能换回图；承接人与后续排查者手上什么都没有，等于把「图片丢失」换成「图片不可达」。
- **附件永久保留**：拒。用户原图长期囤在状态目录里既无用途又扩隐私面；30 天已覆盖「复现、转派、回看」三种真实用途。

**Consequences：**

- 状态目录多两个目录：`briefs/`（任务正文的归档副本，运行时按 `<任务号>.md` 写，`EnsureDirs` 建、`0755`）与 `media/`（消息附件，按消息 id 分目录）。`media/` 不由 `EnsureDirs` 建——它由落盘器自己按 `0700` 建，用户原图不该混进 `0755` 的目录树。
- **`dispatch` 的返回多两格**：`attachments`（平台回认的附件数）与 `build_notes`（嵌图结果/数量偏差/取真值失败）。它们是「任务已建成但没完全长成」的唯一信号，主控读结果文件时必须看。
- **主控的受理路径变短**：「回一句收到 → 一次 dispatch 转发」即可，写正文移到朱贵的执行回合里并行进行。代价是正文质量取决于朱贵的整理，所以朱贵手册的模板与「只整理不创作」是硬规矩，不是建议。
- **平台任务的 description 从此是人话 markdown**，可被承接人直接读；正文里出现内部词汇（主控/派活员/台账/能力 key）就是这层契约破了——所以「整理」限定在用户给的料里，越界就会漏这些词进来。
- 富文本的 `content_v2` **优先于 `content`**（飞书文档：`md` 标签只出现在 `content_v2`，且推荐优先读它；没有 `md` 标签时两份相同）。`md` 标签里的正文按原样保留（markdown 结构、代码块都是最贴近原话的形态），内联图片 `![alt](img_…)` 与 `@` 提及 `<at user_id=…>` 分别改写成可下载占位与 `@名字`；`code_block` 保成围栏、`hr` 保成分隔线——这些从前都被静默丢弃（日志/堆栈就在代码块里）。纯媒体消息不再只剩「`[媒体消息]`」四个字，而是带 key（或路径）的占位；视频消息取视频 `file_key` 而不是封面 `image_key`（后者会把视频换成一张封面图）。
- **改运行时二进制生效**：附件下载依赖飞书应用权限（`im:resource` 一类），已在 2026-11-18 用真实消息验证（HTTP 200、`image/jpeg`、1106754 字节，与消息里的 `width/height` 一致）；凭证仍只走环境变量（密钥卫生不变）。
- 已建的老任务不会回溯修复：HF-16095 的 description 仍是信封原文、类型仍是需求、图片仍需人工补到该任务上。
- **不订阅发起人**：任务由 CLI 的成员身份创建，平台已按 `reason=creator` 自动订阅（HF-16095 的 `task subscriber list` 实测）。飞书侧只有 `open_id`，换不出平台成员身份，硬映射只会订阅错人——要加订阅必须有显式的「飞书 sender → 平台成员」映射源，那是另一件事。
